    What the exam actually asks

    From the Monsoon 2024 midsem paper and the four quiz answer keys in your own course folder — not from a general idea of what a C exam is like.

    • Short definition, with an example — A three-mark question that asks you to define a term and illustrate two of its rules with an example. The example is half the marks — a definition with no example is a half answer.
    • Evaluate an expression by hand — 7%7 + 7/7 - 7*7 >> 1. No computer. This is precedence, integer division and the fact that the shift operators bind below the arithmetic.
    • Predict the output — The most common question in the paper, and the whole reason for the section below. Usually eight to fifteen lines with one surprising construct in them.
    • Fill in the blank so the output is X — A loop header or a printf argument list is blanked and you pick from four options. It tests the same knowledge as output prediction, backwards.
    • Explain the reasoning — Several output questions also ask for the reasoning behind the output you chose. The answer alone does not score full marks, so the explanation lines in this section are the part worth rehearsing.

    Two of the five are output prediction in one form or another, and a third asks you to explain the output rather than just state it. That is what the trace section is for, and why every answer there carries its reasoning.

    0x00

    Absolute basics

    Already comfortable with variables, functions and compiling in some other language? Skip straight to 0x01 — this section exists only to give the rest of the sheet somewhere to land if C is your first language, or your first compiled one.

    What gcc file.c -o prog actually does

    Three separate things happen, in order, and the error message tells you which one failed:

    1. Preprocessing — every #include is replaced by the text of that file, and every #define is substituted, before anything else happens.
    2. Compiling — your C source becomes machine instructions. This is where -Wall -Wextra warnings and most errors come from: a missing semicolon, a type mismatch, a misspelled variable name.
    3. Linking — your compiled code is stitched together with the library code it calls (printf lives in the C standard library, not in your file) into one runnable file.

    "Undefined reference to X" is a linker error, not a compiler one — it means the compiler accepted your code but nothing supplied the actual code for X. Look for a missing #include, a missing source file on the command line, or a missing -l flag.

    The smallest program that does something

    #include <stdio.h>

int main(void) {
    printf("Hello, C\n");
    return 0;
}

    #include <stdio.h> pulls in the declaration of printf so the compiler knows it exists and what it takes. int main(void) is the one function the operating system calls directly when your program starts — int because it returns a whole number, void because it takes no arguments here. Every statement inside ends in a semicolon; the compiler uses that to know where one instruction stops and the next starts, not the line break.

    return 0; at the end of main is not decoration. That number becomes the program's exit status — 0 means success by convention, and C1.1 in the challenges below builds on exactly this.

    Variables, in one paragraph

    A variable is a named, typed storage location. int count = 0; reserves enough memory to hold one whole number, names that memory count, and puts 0 in it right away. The type — int, double, char — tells the compiler how many bytes to reserve and how to interpret the bits in them; a double and an int occupying the same number of bytes hold completely different things. Assignment (count = count + 1;) changes what is stored there without changing the name or the type.

    C never tells you what a variable held before you set it. An uninitialised int total; can print anything, including 0 by pure chance — which is why a program that "looks right" on one run is not proof it is correct. 0x17 below shows a bug exactly this shape, caught with a debugger rather than by staring at the code.

    Compiling and running from the terminal

    gcc -Wall -Wextra -g hello.c -o hello
./hello
echo $status          # fish: exit status of the last command

    -Wall -Wextra turns on warnings the compiler otherwise stays quiet about — nearly all of them are real bugs written in valid syntax. -g keeps debug information in the binary so gdb (0x17) can show you source lines and variable names instead of raw addresses. -o hello names the output file; without it, gcc names the file a.out by default, which is why older tutorials say "run ./a.out".

    Every challenge below tells you to compile with -Wall -Wextra and fix every warning before comparing your output. That is not a style preference — half the bugs in 0x0D compile silently without those flags and only show up as a warning with them.

    0x01

    Getting started

    In plain terms

    A C program is text you write in a file and then hand to another program — a compiler — which turns it into something the machine can actually execute. Nothing runs until you compile it. Of all the functions you write, the system knows how to call exactly one, main, so that is where your program starts and where it ends.

    A C program is a collection of functions. When you run it, the operating system calls exactly one of them — main — and the program ends when main returns. Everything else happens because main asked for it, directly or indirectly.

    The whole program, line by line

    #include <stdio.h>      // library declarations

int main(void) {         // entry point
    printf("Hello, world\n");
    return 0;            // 0 = success
}

    Line 1 pastes in the declarations for printf and friends. C has no built-in printing — without this line the compiler has never heard of printf.

    Line 3 declares a function called main that takes nothing (void) and returns an int. That int is the program's exit status, which the shell can inspect.

    Line 5 returns 0, meaning "finished normally". Any non-zero value conventionally signals an error. Scripts check this.

    Every statement ends in ; and every block is wrapped in { }. The compiler ignores line breaks entirely — the semicolon is what marks the end of a statement.

    Compile and run

    gcc hello.c -o hello     // compile
./hello                  // run (Linux/macOS)
hello.exe                // run (Windows)

// the flags you should always use
gcc -Wall -Wextra -g -std=c11 hello.c -o hello

    C is compiled, not interpreted: gcc turns your text file into a standalone machine-code executable. Nothing needs to be installed on the machine that runs it.

    -o hello names the output; leave it off and you get a file called a.out. -Wall -Wextra switch on warnings — these are not pedantry, they catch genuine bugs like format-string mismatches and unused results. -g embeds debug info so gdb and sanitizers can show you line numbers.

    Treat every warning as an error you haven't hit yet. In C, the compiler warning is often the only thing standing between you and a silent memory bug.

    Command-line arguments

    int main(int argc, char *argv[]) {
    // argc = how many, argv = the strings
    for (int i = 0; i < argc; i++)
        printf("%d: %s\n", i, argv[i]);
    return 0;
}
// ./prog hello 42
//   argc == 3
//   argv[0] == "./prog"   argv[1] == "hello"
//   argv[2] == "42"       argv[3] == NULL

    The shell splits your command on spaces and hands the pieces to your program as an array of strings. argv[0] is the program's own name, so real arguments start at index 1 — which is why argc is always at least 1.

    Everything arrives as text. "42" is a three-byte string, not a number; converting it is your job (see strtol in the stdlib section).

    argv[argc] is always NULL. That is guaranteed, and it is why you can walk the arguments without consulting argc at all.

    Comments, whitespace, naming

    // single line (C99 and later)

/* multi
   line — cannot be nested */

// whitespace is free-form; this compiles fine:
int    main ( void ) { return 0 ; }

    Comments are stripped before compilation, so they cost nothing at runtime. Note that /* */ does not nest — starting a second one inside the first ends at the first */, which silently swallows code.

    Identifiers can use letters, digits and underscore, but must not start with a digit. C is case-sensitive, so count, Count and COUNT are three different names. Avoid leading underscores — those are reserved for the implementation.

    Comment the decision, never the syntax. /* loop over items */ tells a reader nothing they could not see; /* reversed so the newest wins */ tells them why the code is not what they expected.

    0x02

    Types & variables

    In plain terms

    A variable is a named box holding a value. C makes you say up front what kind of value goes in each box — a whole number, a number with a decimal point, a single character — and that choice fixes both how much memory it takes and what arithmetic on it means. Unlike Python, you cannot later put a word in a box you declared for a number.

    A type in C answers two questions: how many bytes do I reserve, and how do I interpret those bytes. The same 32 bits can be an integer, a float, or four characters — the type is what decides. Sizes are only guaranteed as minimums, so anything that must be an exact width belongs in <stdint.h>.

    Declaring & initializing

    int    count = 0;
double ratio = 1.5;
char   grade = 'A';       // single quotes = one char
char  *name  = "Ada";     // double quotes = string

int a, b, c;              // several at once
int uninit;               // holds garbage!
const int MAX = 100;      // cannot be reassigned

    A declaration reserves storage; it does not clear it. An uninitialized local variable contains whatever bytes the previous function left on the stack, which is why the same program can behave differently between runs or between compilers.

    The quotes matter more than they look: 'A' is the single byte 65, while "A" is two bytes — 'A' followed by a terminating '\0'.

    Initialize at the point of declaration, every time. It costs one keystroke and removes an entire category of bug.

    Integer types

    Pick a type by the range you need. Signed types spend one bit on the sign, so an int reaches about ±2 billion, while an unsigned int uses that bit for magnitude and reaches 4 billion — but can never be negative.

    TypeTypical sizeRange (typical)
    char1 byte−128…127 (signedness varies)
    short2 bytes−32,768…32,767
    int4 bytes±2.1 billion
    long4 or 88 on Linux/macOS, 4 on Windows

    Unsigned types wrap on overflow, which is well-defined: 0u - 1 is the maximum value. Signed overflow is undefined behaviour, and the compiler is allowed to assume it never occurs.

    Signed overflow is undefined behaviour; unsigned overflow is defined and wraps. That is why a loop counting down with an unsigned type and testing i >= 0 never ends — it cannot go below zero.

    Floating point

    float       f = 3.14f;   // ~7 digits,  4 bytes
double      d = 3.14;    // ~15 digits, 8 bytes
long double l = 3.14L;   // ≥ double

    Floats store numbers in binary scientific notation, so most decimal fractions have no exact representation — 0.1 is stored as something very slightly off. Errors accumulate across arithmetic, which is why 0.1 + 0.2 == 0.3 is false.

    An unsuffixed literal like 3.14 is a double. Use double by default; float only buys you memory, and on most CPUs no speed.

    Never use == on floats. Compare with a tolerance: fabs(a - b) < 1e-9.

    Fixed-width types (portable code)

    #include <stdint.h>

int8_t   a;   uint8_t   b;   // exactly 8 bits
int16_t  c;   uint16_t  d;
int32_t  e;   uint32_t  f;
int64_t  g;   uint64_t  h;

size_t   n;   // unsigned; sizes and indices
ptrdiff_t k;  // result of subtracting pointers
intptr_t  p;  // an int wide enough to hold a pointer

    The plain types vary by platform, which breaks file formats and network protocols. The stdint.h names are exact everywhere, so use them whenever the byte layout is part of the contract.

    size_t is what sizeof, strlen and malloc all speak in. It is unsigned, so counting a loop down with size_t i and testing i >= 0 loops forever — it never goes below zero.

    Use size_t for anything that is a count or an index of memory, and print it with %zu. Using int there works until the day something is bigger than two billion.

    bool, void and sizeof

    #include <stdbool.h>
bool ok = true;          // C99; before that, use int

void doNothing(void);    // no params, no return value
void *raw;               // pointer to "some type"

printf("%zu\n", sizeof(int));   // 4 — type needs parens
printf("%zu\n", sizeof x);      // variable does not
sizeof arr / sizeof arr[0]      // element count

    sizeof is computed at compile time and yields bytes. The division idiom works because total bytes ÷ bytes per element = element count — but only where the array was declared, since passing it to a function turns it into a pointer and loses the size.

    void means three different things depending on position: no parameters, no return value, or (as void*) a pointer whose target type is deliberately unknown.

    Write sizeof *p rather than sizeof(struct Thing). It cannot go stale when the type of p changes, which is the one way a correct malloc silently becomes a wrong one.

    Type qualifiers

    • const — a promise that this name will not be used to modify the value. Mostly a documentation and safety tool; it lets the compiler reject accidental writes and lets callers know a function won't touch their data.
    • volatile — "this may change without the program changing it". Stops the compiler caching the value in a register. Needed for hardware registers and variables shared with signal handlers; it is not a threading tool.
    • restrict — a promise that no other pointer reaches this memory, which lets the optimizer skip reloads. Break the promise and you get silent wrong answers.
    • _Atomic — C11; reads and writes cannot be torn by another thread.

    const is a promise to the compiler, not a lock on the memory. Its value is that it makes the compiler reject the moment you break your own promise — so put it on every parameter you do not intend to modify.

    Storage classes: lifetime vs visibility

    int g;                // global: visible to every file
static int hidden;    // global, but private to this file
extern int g;         // "exists, defined elsewhere"

void f(void) {
    int local;             // born and dies with the call
    static int calls = 0;  // survives between calls
    calls++;
}

    Two independent questions: how long does it live, and who can see it. A local lives for one call; a global or static lives for the whole program and is zero-initialized before main starts.

    static confusingly answers both, depending on where it sits. At file scope it means "private to this file". Inside a function it means "persistent across calls, still only visible in here".

    static at file scope means private to this file; static inside a function means survives between calls. One keyword, two unrelated jobs, and reading it as the wrong one is a common confusion.

    Literals & escapes

    42      // int          0x2A   // hex → 42
042     // OCTAL → 34!  0b101  // binary (GCC ext)
42U     // unsigned     42L    // long
42ULL   // unsigned long long
1e-3    // double       1.5f   // float

\n \t \\ \' \" \0 \r \a \xFF \101

    A suffix changes the literal's type, which matters in mixed expressions: 1 << 31 overflows a signed int, while 1u << 31 is fine.

    A leading zero means octal. Writing const int mask = 0755; is intentional; writing int minutes = 09; is a compile error, because 9 is not an octal digit.

    Conversion & casting

    int    i = (int)3.9;      // 3 — truncates, no rounding
double d = 7 / 2;         // 3.0! division happens first
double e = 7 / 2.0;       // 3.5
double f = (double)7 / 2; // 3.5

if (-1 < 1u) { /* FALSE — see below */ }

    C converts operands to a common type before it computes. 7 / 2 is integer ÷ integer, so it produces the integer 3 — and assigning that to a double afterwards cannot recover the lost half. Make one operand a double before the division.

    When signed meets unsigned of the same rank, the signed value converts to unsigned. -1 becomes 4,294,967,295, so the comparison above is false. This is a common source of loops that never terminate.

    A cast does not convert a value so much as tell the compiler to stop objecting. If you find yourself adding one to silence a warning, the warning was usually right.

    0x03

    Operators

    In plain terms

    Operators are the symbols that do something to values: + adds, == asks whether two things are equal, && means “and”. The only part that catches people out is precedence — which one happens first when you write several in a row. Brackets settle it, and cost nothing.

    C has a lot of operators and a precedence table almost nobody has memorised. Parentheses cost nothing and have never once made a code review worse.

    Arithmetic & assignment

    +  -  *  /  %        // % = remainder, integers only
++x  --x             // pre:  change, then yield
x++  x--             // post: yield, then change

=  +=  -=  *=  /=  %=  &=  |=  ^=  <<=  >>=

int a = 5, b = 2;
a / b   // 2  — the fraction is discarded
a % b   // 1
-7 / 2  // -3 — truncates toward zero
-7 % 2  // -1 — sign follows the dividend

    The pre/post distinction only matters when you use the result: b = a++ gives b the old value, b = ++a the new one. As a standalone statement they are identical, so prefer i++ in loops out of habit and don't think about it further.

    % works on integers only. For floating point use fmod() from math.h.

    Never write a variable twice in one expression if one of those is a modification. i = i++ + 1 is undefined behaviour, not a clever line — the standard does not say which order the two happen in.

    Comparison & logic

    ==  !=  <  >  <=  >=

&&   // AND — stops at the first false
||   // OR  — stops at the first true
!    // NOT

if (p != NULL && p->value > 0) { ... }
// p->value is never evaluated when p is NULL

    C has no separate boolean type in its core: 0 is false, every other value is true. Comparisons produce exactly 0 or 1.

    Short-circuiting is guaranteed by the standard, not an optimization, so it is safe to rely on it as a guard. The order matters — reverse the two halves above and you dereference NULL.

    Short-circuiting is what makes if (p && p->next) safe. Order the test so the check that prevents a crash comes first — the reverse reads identically and crashes.

    Bitwise

    &    AND      0b1100 & 0b1010 = 0b1000
|    OR       0b1100 | 0b1010 = 0b1110
^    XOR      0b1100 ^ 0b1010 = 0b0110
~    NOT      ~0b1100         = 0b0011
<<   left     1 << 3 = 8   (× 2ⁿ)
>>   right    8 >> 3 = 1   (÷ 2ⁿ)

    These work bit by bit on the binary representation, in parallel across the whole value. That makes them the natural tool for flag sets and hardware registers — one unsigned int holds 32 independent yes/no answers.

    Don't confuse & with &&. 1 & 2 is 0 (no shared bits) but 1 && 2 is 1 (both are truthy).

    Ternary, comma, and the rest

    int max = (a > b) ? a : b;   // an expression, not a
                             // statement — it has a value

for (i = 0, j = n; i < j; i++, j--)   // comma

sizeof x        // bytes occupied
&x              // address of
*p              // value at
a[i]            // identical to *(a + i)
s.field         // member of a struct
p->field        // member through a pointer

    The ternary is useful precisely because it produces a value, so it can appear inside an initializer or an argument where an if cannot. Nesting more than one is where readability goes to die.

    The comma operator evaluates left, throws it away, and yields right. Its only respectable home is a for header.

    The ternary produces a value, so it is the only way to conditionally initialise a const. That is the case worth using it for; the rest is usually an if in disguise.

    Precedence — highest to lowest

    LevelOperatorsAssoc.
    1() [] -> . postfix++ --L → R
    2! ~ ++x --x +x -x (cast) * & sizeofR → L
    3* / %L → R
    4+ −L → R
    5<< >>L → R
    6< <= > >=L → R
    7== !=L → R
    8–10& then ^ then |L → R
    11–12&& then ||L → R
    13?:R → L
    14= += −= etc.R → L
    15,L → R

    The one worth memorising: the bitwise operators sit below the comparisons, which is the opposite of what everyone expects.

    Because bitwise sits below comparison, if (flags & MASK == MASK) compares first and ANDs second — the opposite of what it reads as. Bracket every bitwise test.

    Where precedence actually bites

    if (x & 1 == 0)      // parsed as x & (1 == 0) → x & 0 → 0
if ((x & 1) == 0)    // what you meant

*p++                 // ++ binds tighter: advance p,
                     // dereference the old value
(*p)++               // increment the pointed-to value

a << 1 + 2           // + is higher → a << 3

    The first line is the classic: it compiles cleanly, always evaluates to false, and looks correct at a glance. None of these are bugs the compiler can warn you about, because all four are legal expressions.

    Control flow

    In plain terms

    Code runs top to bottom unless you say otherwise. These are the ways to say otherwise: do this only if something is true, do this repeatedly, stop when a condition changes. Five constructs cover everything you will ever write.

    Five constructs cover everything you'll ever write: if, switch, while, do-while, for. And goto, which has exactly one defensible use.

    if / else if / else

    if (score >= 90) {
    puts("A");
} else if (score >= 80) {
    puts("B");
} else {
    puts("F");
}

if (x) doThis();     // legal, but write the braces

    The condition is any expression: zero is false, non-zero is true. That means if (p) is a perfectly idiomatic null check and if (n) tests "n is not zero".

    Braces are optional around a single statement, and that optionality has caused real security vulnerabilities — adding a second line under a brace-less if silently puts it outside the condition. Always brace.

    Watch for the stray semicolon: if (x); gives the if an empty body, and the block after it runs unconditionally.

    switch

    switch (ch) {
    case 'a':
    case 'A':                 // deliberate fallthrough
        puts("letter A");
        break;                // without this, execution
                              // continues into the next case
    case 'b':
        puts("letter B");
        break;
    default:
        puts("something else");
}

    A switch is a jump table, not a chain of tests: control jumps to the matching label and then keeps running downward until it hits a break. Stacking labels as above is how you deliberately share a body; forgetting the break is how you accidentally do.

    Only integer types work — int, char, enum. You cannot switch on strings or doubles. Every case label must be a compile-time constant.

    Declaring a variable directly inside a case needs its own braces: case 1: { int t = 0; ... break; }

    The three loops

    // for: you know the iteration count up front
for (int i = 0; i < n; i++) { ... }
//   init      test     step

// while: test first, so it may run zero times
while (more_data()) { ... }

// do-while: body first, so it always runs once
do { prompt(); } while (!valid);

for (;;) { ... }     while (1) { ... }   // infinite

    All three are interchangeable in power — pick the one that states your intent. for when there's a counter, while when you're waiting on a condition, do-while when the first attempt must happen before you can judge it (menus, input validation, retry loops).

    The for header's three parts are all optional. Declaring the counter inside the header (C99) keeps it scoped to the loop, which is almost always what you want.

    Declare the counter in the for itself. A counter that outlives its loop is a variable two loops can accidentally share, and that bug looks like the second loop being wrong.

    break, continue, and the one good goto

    for (int i = 0; i < n; i++) {
    if (a[i] < 0) continue;    // skip the rest of
                               // this iteration
    if (a[i] == target) break; // leave the loop entirely
}

// goto's respectable use: unwinding cleanup
FILE *f = fopen("x", "r");
if (!f) goto fail;
char *buf = malloc(1024);
if (!buf) goto close_file;
// ... work ...
free(buf);
close_file: fclose(f);
fail:       return -1;

    break only escapes the innermost loop or switch. To leave nested loops you need a flag, a goto, or to extract the loops into a function and return.

    C has no destructors, so every early exit must release whatever was acquired so far. The label-cascade pattern above puts that cleanup in one place instead of duplicating it at every failure point — which is why you'll see it throughout the Linux kernel.

    The one defensible goto is forward, to a single cleanup label at the end of a function. Every kernel function that allocates more than one thing is written this way, and it is clearer than the nested-if alternative.

    0x05

    Functions

    In plain terms

    A function is a named piece of code you can run from somewhere else by writing its name. You hand it values going in, and it hands one value back. The part specific to C: the function receives a copy of what you gave it, so changing that copy leaves your original untouched.

    C passes arguments by value, always. The function receives a private copy and anything it does to that copy is invisible to the caller. To let a function reach your variable, you hand it the address instead — that is the entire reason pointers appear in ordinary code.

    Declare, define, call

    // prototype (declaration) — usually in a .h file
int add(int a, int b);

// definition — the actual body
int add(int a, int b) { return a + b; }

int sum = add(2, 3);              // call
void greet(void) { puts("hi"); }  // returns nothing

    The compiler reads top to bottom and needs to know a function's signature before it sees a call, so it can check argument types and generate the right code. A prototype is that advance notice — it lets you define functions in any order and put the declarations in a header for other files.

    Write (void), not (), for a function taking no parameters. Empty parentheses mean "unspecified arguments" in older C and disable checking.

    A function with no prototype in scope used to be assumed to return int. Modern compilers reject it instead — which is exactly the implicit declaration error, and it always means a missing #include.

    By value vs by pointer

    void broken(int x)  { x = 99; }   // edits the copy
void works (int *x) { *x = 99; }  // edits the original

int n = 1;
broken(n);      // n is still 1
works(&n);      // n is now 99

// arrays are the exception: they decay to pointers,
// so the callee CAN modify the caller's data
void zero(int a[], size_t n) {
    for (size_t i = 0; i < n; i++) a[i] = 0;
}

    Read works(&n) as "here is where n lives, go edit it". Inside, *x = 99 means "write 99 to the place x points at". The pointer itself is still passed by value — the function gets a copy of the address — but the address still leads to your variable.

    Arrays feel like an exception but follow the same rule: what's copied is the address of the first element, not the contents.

    If a function needs to change something you own, it takes a pointer to it. There is no other mechanism in C — no references, no output parameters of any other kind. Every “why did my variable not change” question is this.

    Returning more than one value

    // option 1: out-parameters
void divmod(int a, int b, int *q, int *r) {
    *q = a / b;
    *r = a % b;
}
int q, r;  divmod(17, 5, &q, &r);

// option 2: return a struct (a real copy, safe)
typedef struct { int q, r; } DivResult;
DivResult divmod2(int a, int b) {
    return (DivResult){ a / b, a % b };
}

    C returns exactly one value, so multi-result functions either write through pointers or bundle the results into a struct. The common hybrid: return a status code, deliver the payload through an out-parameter — which is how most of the standard library and POSIX behave.

    Returning a struct is safe; returning a pointer to a local is not. The struct is copied, the local is destroyed.

    Function pointers

    // op points to a function (int,int) → int
int (*op)(int, int) = add;
int r = op(2, 3);

// typedef makes them survivable
typedef int (*BinOp)(int, int);
BinOp table[] = { add, sub, mul };
int v = table[1](10, 4);

// the classic: qsort's comparator
int cmp(const void *a, const void *b) {
    int x = *(const int *)a, y = *(const int *)b;
    return (x > y) - (x < y);   // -1, 0, or 1
}
qsort(arr, n, sizeof arr[0], cmp);

    Code lives in memory too, so it has an address, and a variable can hold it. That gives you callbacks, plugin tables and dispatch without any object system: qsort can sort anything precisely because you supply the comparison.

    The parentheses around *op are load-bearing — without them int *op(int,int) declares a function returning int*. Note the comparator returns a sign, not a difference; subtracting can overflow.

    Read the declaration with the name first: int (*f)(int) is “f is a pointer to a function taking int and returning int”. The parentheses around *f are load-bearing — without them it is a function returning a pointer instead.

    Variadic functions

    #include <stdarg.h>

int sum(int count, ...) {
    va_list ap;
    va_start(ap, count);       // start after `count`
    int total = 0;
    for (int i = 0; i < count; i++)
        total += va_arg(ap, int);   // you state the type
    va_end(ap);
    return total;
}
sum(3, 10, 20, 30);   // 60

    This is how printf works. The catch is that C keeps no record of how many arguments arrived or what types they were — va_arg just reads the next slot and trusts the type you name.

    So the count has to come from somewhere: an explicit parameter, a sentinel like NULL at the end, or a format string. Get it wrong and you read past the argument list, which is exactly the printf("%s", 42) crash.

    The count or a terminator has to come from somewhere you control — a leading count, a format string, or a NULL at the end. A variadic function cannot detect that it ran out of arguments; it just reads whatever is next.

    Recursion & inline

    unsigned long fact(unsigned n) {
    if (n <= 1) return 1;     // base case FIRST
    return n * fact(n - 1);   // shrinks toward it
}

static inline int square(int x) { return x * x; }

    Every recursive call allocates a fresh stack frame for its own parameters and locals. That's what makes recursion work — each level has private variables — and also what limits it: the stack is typically 1–8 MB, so a few tens of thousands of frames will overflow it and crash.

    A recursive function needs a base case that stops it, and each call must move measurably closer to that base case. inline is only a hint asking the compiler to paste the body at the call site; modern compilers largely decide for themselves.

    Recursion depth is bounded by the stack, and blowing it is a segfault with no message. Anything whose depth is driven by user input — parsing nested data, walking a filesystem — wants a loop and an explicit stack.

    0x06

    Pointers & memory

    In plain terms

    Every byte of memory has a number, the way every house on a street has a number. A pointer is a variable that holds one of those numbers instead of holding a value. That is the whole idea. Almost everything people find hard about C is a consequence of it, and very little of C makes sense before it lands — so if only one section here gets read twice, make it this one.

    Memory is one enormous numbered array of bytes. A pointer is just a variable holding one of those numbers. That's the whole concept — arrays, strings, structs on the heap, linked lists and function callbacks are all consequences of it.

    The two operators

    int  x = 42;
int *p = &x;              // & = "address of x"

printf("%d\n",  x);       // 42
printf("%p\n", (void*)p); // 0x7ffd10 — the address
printf("%d\n", *p);       // 42 — * = "value living there"

*p = 99;                  // write through the pointer
printf("%d\n", x);        // 99 — x itself changed

    Think of x as a labelled box and &x as its street address. p is a different box that stores that address. Dereferencing with *p means "go to that address and use what's there" — so writing through p changes x, because they are the same box reached two ways.

    The * symbol has two jobs. In a declaration it means "this is a pointer". In an expression it means "go there now".

    Reading a pointer declaration

    int  *p;        // pointer to int
int **pp;       // pointer to pointer to int
int  *a[10];    // array of 10 pointers to int
int (*a)[10];   // pointer to an array of 10 ints
int  *f(void);  // function returning int*
int (*f)(void); // pointer to function returning int

int *a, b;      // a is int*, b is a plain int!

    Start at the name and read outward, going right before left: [] and () bind tighter than *, and parentheses override that. So in int *a[10] the [10] applies first ("array of 10"), then the * ("of pointers"), then int.

    The last line trips up everyone: the * attaches to the variable, not the type. Declare one pointer per line and the problem disappears.

    cdecl-style reading aloud is not a party trick; it is how you check a declaration you did not write. Start at the name, go right, then left, and say each piece out loud.

    const and pointers — two different locks

    const int *p;        // pointer to const int
int const *p;        // identical
  // *p = 5;   ERROR    |  p = &other;  fine

int *const p = &x;   // const pointer to int
  // *p = 5;   fine     |  p = &other;  ERROR

const int *const p = &x;   // both locked

    There are two things that could be constant: the pointer, or the thing it points to. The rule is that const applies to whatever is immediately to its left — or to its right if there's nothing on the left. * is the dividing line.

    The first form is by far the common one. A function taking const char *s is telling you it will read your string and not modify it, which is why strlen and strcmp declare their parameters that way.

    const char *p is the one you want almost every time: the text cannot be changed, the pointer can be moved. Put it on every string parameter you only read.

    Pointer arithmetic

    int a[5] = {10,20,30,40,50};
int *p = a;          // array name decays to &a[0]

p + 1                // moves 4 bytes (one int), not 1
*(p + 2)             // 30 — exactly what a[2] means
p++;                 // now points at a[1]
p - a                // 1 — measured in ELEMENTS

for (int *q = a; q < a + 5; q++) printf("%d ", *q);

    Arithmetic on pointers is scaled by the size of the pointed-to type automatically, so p + 1 always means "the next element" regardless of whether that's 1 byte or 400. This is why void* can't do arithmetic — the step size is unknown.

    And this is what indexing is: a[i] is defined as *(a + i). Which, amusingly, makes 3[a] legal C.

    Arithmetic is only valid within a single array, plus one position past its end (useful as a loop bound, but never dereference it).

    NULL and void*

    int *p = NULL;       // "deliberately points at nothing"
if (p == NULL) ...   // or simply  if (!p)

void *raw = malloc(64);   // typeless pointer
int  *nums = raw;         // no cast needed in C
// void* cannot be dereferenced or advanced

    NULL is a reserved address that no valid object occupies, so it can safely mean "empty". It's the standard return for functions that failed to produce a pointer, and the standard end-marker for linked structures.

    Dereferencing NULL crashes immediately — which is the good outcome. A pointer holding stale garbage may silently corrupt unrelated data and surface as a bug three functions away.

    void* is C's escape hatch for generic code: malloc returns one because it has no idea what you'll store, and qsort takes them because it sorts anything.

    Check for NULL at the point you receive a pointer, not at the point you use it. By the time you dereference it, the function that returned it is off the stack and the reason it failed is gone.

    Pointer to pointer

    int   x  = 5;
int  *p  = &x;
int **pp = &p;
**pp = 10;       // x is now 10

// why it exists: changing the CALLER'S pointer
void alloc_it(int **out) {
    *out = malloc(sizeof **out);
    **out = 7;
}
int *q;  alloc_it(&q);   // q now points at the block

    Same rule as before, one level up. To modify an int a function needs int*; to modify an int* it needs int**. Pass alloc_it a plain int* and it would set a copy, leaving your q uninitialized.

    You'll meet this in three places: allocator functions like the one above, arrays of strings (char **argv), and any linked-list code that has to update the caller's head.

    You need one more * than the thing you are changing. Changing an int needs int *; changing where a pointer points needs int **. Count the levels rather than guessing.

    Where memory comes from

    • Stack — locals and parameters. Allocated and freed automatically as functions enter and exit, extremely fast, but fixed in size (typically 1–8 MB) and gone the moment the function returns.
    • Heap — whatever you malloc. You decide when it dies, it can be large, and it outlives the function that created it — at the price of having to free it yourself.
    • Static / global — lives for the entire program, zero-initialized before main runs.
    • Text / read-only — the compiled code and string literals. Writing here is undefined and usually a segfault.
    char *bad(void) {
    char buf[64];            // on the stack
    return buf;              // buf ceases to exist HERE
}
char *good(void) {
    char *buf = malloc(64);  // on the heap
    return buf;              // valid — caller must free()
}

    The question to ask about any pointer: does the thing it points to still exist? That single question catches most C memory bugs.

    malloc / calloc / realloc / free

    #include <stdlib.h>

int *a = malloc(n * sizeof *a);   // uninitialized bytes
int *b = calloc(n, sizeof *b);    // zero-filled

if (a == NULL) { /* allocation failed */ }

// growing: never assign realloc's result to `a`
int *tmp = realloc(a, 2 * n * sizeof *a);
if (tmp == NULL) { free(a); return -1; }
a = tmp;

free(a);
a = NULL;

    malloc asks for a number of bytes and hands back the address of a block that stays yours until you free it. It does not clear the memory; calloc does, and also checks the multiplication for overflow, which makes it the safer default for arrays.

    realloc may move the block to a bigger spot and returns the new address — so it returns NULL on failure. Assigning straight to a would overwrite your only reference to the old block and leak it.

    Write sizeof *a, not sizeof(int). If you later change a's type, the allocation size follows automatically.

    Dynamic 2D arrays

    // A) one flat block — one malloc, one free, fast
int *grid = malloc(rows * cols * sizeof *grid);
grid[r * cols + c] = 1;          // index by hand
free(grid);

// B) array of row pointers — real [r][c] syntax
int **m = malloc(rows * sizeof *m);
for (int i = 0; i < rows; i++)
    m[i] = malloc(cols * sizeof *m[i]);
m[r][c] = 1;
for (int i = 0; i < rows; i++) free(m[i]);  // rows first!
free(m);

    Option A keeps the whole grid contiguous, so it's cache-friendly and impossible to half-free. The r * cols + c formula is just "skip r full rows, then c elements".

    Option B buys nicer syntax at the cost of many allocations and scattered rows. Free them in reverse order of creation — free the outer array first and you've lost the addresses of every row.

    Prefer the single contiguous block. One allocation and one free means there is no half-freed state to get wrong, and no partial-failure path to write.

    The four memory bugs

    • Leak — allocated, never freed. The program's memory use climbs until it is killed. Harmless in a five-second script, fatal in a server.
    • Use-after-free — reading or writing a block you already returned. It usually appears to work, because the bytes are still there, right up until the allocator reuses them.
    • Double free — freeing the same block twice corrupts the allocator's bookkeeping, and the crash surfaces in some unrelated malloc later.
    • Buffer overflow — writing past the end of a block, overwriting whatever sat next to it. The classic security hole.

    None of these reliably crash at the scene of the crime, which is why you don't debug them by reading the code — you run the tools:

    gcc -fsanitize=address,undefined -g prog.c -o prog
valgrind --leak-check=full ./prog

    0x07

    Arrays & strings

    In plain terms

    An array is several values of the same kind stored end to end, reached by position: a[0] is the first, a[1] the second. A C string is nothing more than an array of characters with a zero byte marking the end. There is no separate string type and nothing tracks the length for you.

    An array is a run of identical values laid end to end. A C string is nothing more than an array of char ending in a zero byte — there is no length field, no capacity, and nothing anywhere checks your bounds.

    Arrays

    int a[5];                    // 5 ints of garbage
int b[5] = {1,2,3,4,5};
int c[5] = {1,2};            // remaining slots → 0
int d[]  = {1,2,3};          // size inferred: 3
int e[5] = {0};              // all zero
int f[5] = {[2] = 7};        // designated (C99)

size_t n = sizeof a / sizeof a[0];   // 5

    The elements sit contiguously in memory, which is why indexing is a single multiply-and-add and why arrays are so cache-friendly. The size must be a compile-time constant (unless you use a VLA), and it can never change afterwards.

    Partial initializers zero-fill the rest, which is what makes {0} the idiom for clearing an array. Indices run 0 to n-1; writing a[5] on a five-element array is undefined behaviour, not an error — the compiler won't stop you and neither will the CPU.

    An array passed to a function becomes a pointer and the length is gone. Pass the length beside it, every time — sizeof inside the function gives you the size of a pointer, which is a bug that compiles and runs.

    Multidimensional arrays & VLAs

    int grid[3][4];                // 3 rows of 4
int m[2][3] = {{1,2,3},{4,5,6}};
m[1][2];                       // 6

// stored row-major: m[1][2] sits at offset 1*3+2

void print(int rows, int a[][4]) { ... }
// every dimension but the first must be given

void f(int n) { int tmp[n]; }  // VLA (C99)

    A 2D array is really one flat block; the second dimension is just arithmetic. That's why the compiler needs the column count to index it — without knowing a row is 4 wide, it cannot find row 1.

    VLAs size themselves at runtime but live on the stack, so a large or attacker-controlled n will blow it. They're also optional in C11. For anything sizeable, malloc instead.

    A VLA's size comes from a runtime value, so a large or attacker-controlled size puts an unbounded amount on the stack. The kernel bans them outright and you should treat them the same way outside toy code.

    Strings and the null terminator

    char s[] = "hi";     // {'h','i','\0'} — 3 bytes
char t[6] = "hi";    // h i \0 \0 \0 \0
char *lit = "hi";    // points at READ-ONLY memory
// lit[0] = 'H';     // undefined behaviour

strlen(s);           // 2 — walks until it finds \0
sizeof s;            // 3 — the whole array

for (char *p = s; *p; p++) putchar(*p);

    Every string function finds the end by scanning for the zero byte. Lose that byte — by filling an array exactly to its edge, or by using strncpy at full width — and every subsequent strlen, printf or strcpy reads off into whatever follows.

    It also means strlen is O(n), so calling it in a loop condition rescans the string every iteration. And always budget strlen + 1 bytes when allocating.

    char s[] = "hi" is a writable copy on the stack. char *s = "hi" points into read-only memory. They look almost identical and behave completely differently.

    Array-to-pointer decay

    void f(int a[]) {          // this is really int *a
    sizeof a;              // 8 — the size of a POINTER
}                          // the length is simply gone

void f(int *a, size_t n);  // so pass it explicitly

int a[3], b[3];
// a = b;                  ERROR — not assignable
memcpy(a, b, sizeof a);    // copy contents
// if (a == b)             compares ADDRESSES
memcmp(a, b, sizeof a) == 0;   // compares contents

    In almost every context an array's name evaporates into a pointer to its first element. This is why passing an array to a function is cheap regardless of size — and why the function has no idea how big it is.

    Decay is also why arrays can't be assigned or compared with ==: both operands become addresses, so you'd be asking whether two different arrays live at the same place.

    An array pointer and its length are a single unit of information. Pass them together, always.

    Structs, unions, enums, typedef

    In plain terms

    A struct bundles several values into one named thing — a point with an x and a y, a book with a title and a year. It is how you invent your own types in a language that ships almost none of them.

    A struct lays several values side by side into one compound value. A union overlays them on the same bytes so only one is valid at a time. An enum gives names to a set of integers. typedef just gives any of them a shorter name.

    Declaring and using a struct

    struct Point { int x; int y; };

struct Point p1;             // "struct" is required
struct Point p2 = {3, 4};    // in declaration order
struct Point p3 = {.y = 4};  // by name (C99); x = 0
p1.x = 10;

struct Point p4 = p2;        // copies every field

    The declaration defines a type, not a variable — no memory is reserved until you declare one. Members are stored in the order you write them, so the struct is a template for a chunk of memory.

    Unlike arrays, structs can be assigned and passed by value; the whole thing is copied field by field. That copy is shallow, though: if a member is a pointer, both structs end up pointing at the same data.

    Designated initializers are worth the habit — {.y = 4} survives someone reordering the fields later, while {0, 4} silently changes meaning.

    typedef — dropping the "struct"

    typedef struct { int x, y; } Point;
Point p = {1, 2};       // no keyword needed

// named AND typedef'd — required for self-reference
typedef struct Node {
    int data;
    struct Node *next;  // the tag must be used here
} Node;

typedef unsigned long long u64;
typedef int (*Callback)(void *);

    typedef creates an alias, nothing more — no new type, no checking. Its real value is on declarations that are painful to read, like function pointers.

    The self-referencing case is the one that catches people: inside the braces the typedef name doesn't exist yet, so a node pointing to another node must use the struct tag. Hence the apparent redundancy of naming it twice.

    Typedef the struct, but keep the tag: typedef struct Node Node;. Without the tag the type cannot refer to itself, which every linked structure needs to do.

    Pointers to structs: the arrow

    Point *p = &pt;

(*p).x = 5;      // correct, ugly, parens mandatory
p->x    = 5;     // identical — always write this

Point *q = malloc(sizeof *q);
q->x = 1;  q->y = 2;
free(q);

void move(Point *p, int dx) { p->x += dx; }

    -> is pure shorthand for "dereference, then select a member". The parentheses in the long form are required because . binds tighter than *, so *p.x would try to dereference p.x.

    Beyond syntax, this is how you avoid copying: passing a 200-byte struct by value copies 200 bytes on every call, while a pointer copies 8 — and lets the function modify the original. Use const Point * when it shouldn't.

    p->x dereferences. If p could be NULL, the arrow is the crash site — so the check belongs above it, not inside the function you are about to call.

    Nesting & arrays of structs

    typedef struct {
    char name[32];      // array member: storage inline
    Point pos;          // nested struct
    int  scores[3];
} Player;

Player team[4] = {
    { "Ada", {0,0}, {10,20,30} },
    { .name = "Bob", .pos = {5,5} },
};

team[0].pos.x = 9;
strcpy(team[1].name, "Bobby");   // not =

    Structs nest to any depth and each member lives inside its parent's memory, so one Player is a single self-contained block. Declaring char name[32] rather than char *name means the text is stored in the struct — no separate allocation, no dangling pointer, but a fixed 31-character limit.

    That inline array is also why you assign it with strcpy: arrays can't be assigned, even inside structs.

    char name[32] stores the text inside the struct and copies with it; char *name stores an address and does not. Copying a struct is always a shallow copy, and that distinction is the whole of it.

    Padding & alignment

    struct Bad  { char a; int b; char c; };  // 12 bytes
struct Good { int b; char a; char c; };  // 8 bytes

printf("%zu\n", sizeof(struct Bad));
offsetof(struct Bad, c);   // <stddef.h>

    CPUs read memory fastest when a 4-byte value sits at an address divisible by 4, so the compiler inserts invisible padding bytes to keep each member aligned. In Bad, three bytes of padding follow a to line up b, and three more trail c so an array of them stays aligned.

    Ordering members from largest to smallest usually squeezes the padding out — 12 bytes down to 8 here, which matters when you have millions of them.

    Never memcmp two structs to compare them. The padding bytes are uninitialized garbage, so identical-looking structs can compare unequal.

    Bit fields

    struct Flags {
    unsigned int visible : 1;   // 1 bit  → 0 or 1
    unsigned int type    : 3;   // 3 bits → 0..7
    unsigned int id      : 12;
};
struct Flags f = {0};
f.visible = 1;

    Bit fields let you pack several small values into one machine word while still accessing them by name — 16 bits here instead of 12 bytes for three separate ints.

    The catch is that the standard doesn't fix the layout: bit order, straddling, and padding are all implementation-defined. Fine for saving memory; unreliable for parsing a network packet or hardware register, where explicit masks and shifts are the portable choice.

    Bit fields are for saving memory in a struct you control, never for laying out a hardware register or a file format. The standard does not fix the order or the padding, so the layout is the compiler's choice, not yours.

    Unions

    union Value { int i; float f; char bytes[4]; };
// size = the largest member; all share one address

union Value v;
v.i = 65;
// reading v.f now is not meaningful — only the
// member you last WROTE holds a valid value

// the safe pattern: a tagged union
typedef struct {
    enum { INT, FLT, STR } tag;   // what's inside?
    union { int i; float f; char *s; } as;
} Var;

    Where a struct is "all of these at once", a union is "one of these at a time", overlapping in the same bytes. It's how you build a variable that can hold any one of several types without paying for all of them.

    A union has no idea which member is currently live, so you must track that yourself — that's the tag field above. Without it, a union is just a loaded gun; with it, it's how interpreters and JSON parsers represent values.

    A union with no tag beside it is a bug waiting to happen. Always pair it with an enum saying which member is live, and read only that member — the compiler will not check this for you.

    Enums

    enum Color { RED, GREEN, BLUE };   // 0, 1, 2
enum Status { OK = 200, NOTFOUND = 404 };

enum Color c = GREEN;
switch (c) { case RED: ...; }

typedef enum { MON, TUE, WED, DAY_COUNT } Day;
// DAY_COUNT == 3 — a count that self-updates

    Enums replace scattered magic numbers with names the debugger and reader can both see. Values auto-increment from 0 unless you set one, after which counting resumes from there.

    They are still just int underneath — nothing stops you assigning 7 to a Color. The trailing-count trick is a genuinely useful idiom: add a day and DAY_COUNT updates itself, so your array sizes and loop bounds stay correct.

    Switch on an enum with no default case. The missing default is what makes the compiler warn you about the case you forgot on the day you add a new value.

    Linked list — the canonical example

    typedef struct Node {
    int data;
    struct Node *next;   // NULL marks the end
} Node;

Node *push(Node *head, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return head;
    n->data = v;
    n->next = head;      // old list hangs off the new node
    return n;            // caller must reassign head
}

void print(const Node *n) {
    for (; n; n = n->next) printf("%d ", n->data);
}

void destroy(Node *n) {
    while (n) { Node *next = n->next; free(n); n = next; }
}

    This is the payoff for everything in this section: a structure that grows one node at a time, each node knowing only where the next one lives. No contiguous block, no fixed capacity — insertion at the front is O(1) no matter how long the list is.

    Note destroy: you must save n->next before freeing n, because after the free the node's memory is no longer yours to read. Getting that backwards is the most common use-after-free in beginner C.

    In the free loop, read next before you free the node. After the free that field is no longer yours to read, and the loop usually appears to work anyway — until it does not.

    Opaque types & flexible arrays

    // header: callers see a name, never the fields
typedef struct Stack Stack;
Stack *stack_new(void);
void   stack_push(Stack *, int);

// struct + payload in ONE allocation
typedef struct {
    size_t len;
    char   data[];        // must be the last member
} Buffer;

Buffer *b = malloc(sizeof *b + n);
b->len = n;

    Declaring the struct without defining it gives callers a type they can hold pointers to but cannot inspect or allocate. That's C's encapsulation: the layout lives in one .c file, so you can change it without recompiling anyone else. FILE works exactly this way.

    A flexible array member has no size in the struct; you allocate the header plus however many bytes you need, and the data sits immediately after. One allocation, one free, and the payload is adjacent in cache.

    An opaque type is enforced by the compiler rather than by convention: code that cannot see the fields cannot depend on them, so you can change the layout without breaking a caller.

    stdio.h & format strings

    In plain terms

    Printing to the screen and reading what gets typed in. printf takes a template with placeholders like %d and fills them from the values you pass. It cannot check that you passed the right kinds of value, which is why the wrong placeholder prints nonsense instead of complaining.

    Input and output — and the single most common source of "why is it printing garbage". printf cannot see the types of its arguments; it believes the format string absolutely. If the two disagree, it reads the wrong bytes and prints nonsense or crashes.

    printf specifiers

    SpecTypeExample out
    %d %iint-42
    %uunsigned int42
    %ld / %lldlong / long long42
    %zusize_t42
    %fdouble3.140000
    %.2fdouble, 2 decimals3.14
    %escientific3.14e+00

    The length modifiers exist because C promotes small types when passing them to variadic functions. %d reads 4 bytes; hand it a long long and the remaining 4 bytes stay in the queue, corrupting every argument after it.

    Compile with -Wformat on, which -Wall gives you. It is the only thing standing between a mismatched specifier and a program that prints convincing nonsense.

    Width, precision, flags

    printf("%5d",    42);      // "   42"   min width 5
printf("%-5d|",  42);      // "42   |"  left align
printf("%05d",   42);      // "00042"   pad with zeros
printf("%+d",    42);      // "+42"     always show sign
printf("%8.3f",  3.14159); // "   3.142"
printf("%.*f", 2, 3.14159);// "3.14" — precision from
                           // an argument at runtime
printf("%10s|", "hi");     // "        hi|"
printf("%.3s", "hello");   // "hel" — max chars

    The grammar is %[flags][width][.precision][length]specifier. Width is a minimum — the value is never truncated to fit, so column alignment breaks if a value is wider than you budgeted.

    Precision changes meaning by type: decimal places for %f, significant digits for %g, maximum characters for %s. That last one is a handy way to print a fixed-width field that might not be null-terminated.

    %*d takes the width as an argument, so a column width computed at runtime does not need the format string built by hand. Building format strings at runtime is how format-string vulnerabilities happen.

    Output functions

    printf("x = %d\n", x);            // to stdout
fprintf(stderr, "error: %s\n", m); // to stderr
puts("adds a newline for you");
putchar('A');

char buf[64];
snprintf(buf, sizeof buf, "%d-%d", a, b);  // into a string

    Send diagnostics to stderr, not stdout. They stay visible when the user pipes your output somewhere, and stderr is unbuffered so the message appears even if the program then crashes.

    Use snprintf, never sprintf. sprintf takes no size limit and writes as many bytes as the result needs — a buffer overflow waiting for input longer than you expected.

    Reading input

    int n;
if (scanf("%d", &n) != 1) { /* not a number */ }
                     // ^ & is required: scanf writes
                     //   through a pointer

char line[256];
if (fgets(line, sizeof line, stdin)) {
    line[strcspn(line, "\n")] = '\0';   // strip newline
}

char word[256];
scanf("%255s", word);   // bounded: 255 chars + '\0'

    scanf returns the number of items it successfully converted, so checking that return is how you distinguish "read a number" from "the user typed hello". Ignore it and n silently keeps its old value.

    An unbounded %s has the same flaw as sprintf — it writes however much the user types. Give it a width, or read whole lines with fgets and parse them afterwards.

    gets() cannot be used safely at all and was removed from the language in C11. If you see it in a tutorial, distrust the tutorial.

    Why scanf then fgets goes wrong

    int age;  char name[50];
scanf("%d", &age);       // consumes "25", leaves '\n'
fgets(name, 50, stdin);  // reads that '\n' → empty!

// fix A: drain the rest of the line
int ch;
while ((ch = getchar()) != '\n' && ch != EOF) { }

// fix B (better): read lines, then parse them
char line[256];
fgets(line, sizeof line, stdin);
sscanf(line, "%d", &age);

    scanf("%d") stops as soon as the digits end and leaves the newline sitting in the input buffer. fgets then reads up to the first newline — which is immediately there — and returns an empty string without ever pausing for the user.

    Fix B avoids the whole class of problem: consume input a line at a time so the buffer is always in a known state, and do the parsing separately.

    File I/O

    FILE *f = fopen("data.txt", "r");
if (!f) { perror("fopen"); return 1; }   // ALWAYS check

char line[256];
while (fgets(line, sizeof line, f)) {    // NULL at EOF
    fputs(line, stdout);
}
fclose(f);

// modes: "r" read | "w" truncate or create
//        "a" append | "r+" read and write
//        add "b" for binary: "rb", "wb"

    fopen returns a FILE* handle or NULL — the file may not exist, or you may lack permission, and continuing with a NULL handle segfaults immediately. perror prints your message plus the actual reason.

    Mind that "w" truncates an existing file to zero length the moment it opens, before you write anything. Use "a" if you meant to add to it.

    Output is buffered, so data may sit in memory until fclose or fflush. Skip the fclose and a crash can lose everything you "wrote".

    Binary I/O & seeking

    fwrite(arr, sizeof arr[0], n, f);   // returns items written
size_t got = fread(buf, 1, sizeof buf, f);

fseek(f, 0, SEEK_END);     // SEEK_SET / _CUR / _END
long size = ftell(f);
rewind(f);

if (feof(f))   /* reached end of file */;
if (ferror(f)) /* a real I/O error */;

    Binary I/O copies raw bytes, so it's fast and exact — but the file then depends on your machine's integer sizes, padding and byte order. Don't use it for anything another program or platform must read.

    Both functions return the count actually transferred, which can be less than you asked for. That's your end-of-file and error signal.

    Read characters into an int, not a char: EOF is −1 and would be indistinguishable from a legitimate byte.

    Standard library

    In plain terms

    Everything C gives you for free lives in a handful of files you have to ask for by name with #include. There is far less here than in Python or R — no lists, no dictionaries, no built-in text type. Knowing what is here is what stops you writing it again by hand.

    C's library is small by modern standards — no containers, no string type, no networking. What it does give you is the byte-level toolkit, and a general rule: for every function that writes into a buffer, prefer the variant that takes a size.

    string.h — copying & comparing

    CallDoes
    strlen(s)length, excluding \0
    strcpy(d,s)copy — unbounded, dangerous
    strncpy(d,s,n)copy ≤ n — may not terminate
    strcat(d,s)append to d
    strncat(d,s,n)append ≤ n chars
    strcmp(a,b)0 equal, <0 a sorts first, >0 b
    strncmp(a,b,n)compare first n only
    strchr(s,c)pointer to first c, else NULL

    strcmp returns an ordering, not a boolean — so equality is == 0, and treating the result as true/false inverts your logic. The destination of any copy must already have room; none of these allocate.

    if (strcmp(a, b)) is true when the strings differ. It reads like “if equal” and means the opposite, which is why the explicit == 0 is worth always writing.

    string.h — raw memory

    memset(buf, 0, sizeof buf);      // fill with one byte
memcpy(dst, src, n);             // must NOT overlap
memmove(dst, src, n);            // safe when they overlap
memcmp(a, b, n);                 // compare n bytes
memchr(buf, 'x', n);             // find a byte

    These ignore null terminators entirely and just move bytes, so they work on any type — structs, int arrays, anything. They also count in bytes, not elements, so an int array needs n * sizeof *a.

    memcpy may copy in any order, which corrupts data when source and destination overlap (shifting an array left by one, say). memmove handles that correctly for a tiny cost.

    memset(arr, 1, n) does not fill an int array with 1s — it sets every byte to 1, giving 0x01010101. Only 0 works as expected.

    Common string tasks

    // safe copy into a fixed buffer
char dst[32];
snprintf(dst, sizeof dst, "%s", src);

// compare (NOT ==, which compares addresses)
if (strcmp(a, b) == 0) puts("equal");

// tokenize — note strtok WRITES into s
char s[] = "a,b,c";
for (char *t = strtok(s, ","); t; t = strtok(NULL, ","))
    puts(t);

// join onto the heap: +1 for the terminator
char *j = malloc(strlen(a) + strlen(b) + 1);
strcpy(j, a);  strcat(j, b);

    snprintf is the reliable way to copy a string: it always terminates and never exceeds the buffer, unlike strcpy (no limit) or strncpy (may not terminate).

    strtok replaces each delimiter with '\0' and returns pointers into your buffer, so it destroys the original and cannot be applied to a string literal. It also keeps hidden state between calls, so you can't tokenize two strings at once.

    snprintf returns the length it would have written. A return value at or above your buffer size means it truncated — that return value is the only way to find out.

    Parsing numbers safely

    #include <stdlib.h>

    atoi("abc") returns 0, which is indistinguishable from the user genuinely typing "0" — so it cannot be used on input you don't control.

    strtol writes into end the position where it stopped reading, which lets you tell all three failure modes apart: nothing parsed, partially parsed, or out of range. Reset errno to 0 first, since the library never clears it on success.

    Three separate failures to check after strtol: nothing was consumed, something was left over, and the value did not fit. atoi reports none of them, which is why it has no place on input you did not write.

    ctype.h

    isalpha(c) isdigit(c) isalnum(c) isspace(c)

    Classification without hardcoding ASCII values, which keeps your code correct under other locales and character sets.

    The cast matters: these take an int that must be either EOF or representable as unsigned char. Plain char may be signed, so a byte above 127 arrives as a negative number and indexes off the front of the lookup table.

    Cast the argument to unsigned char. Passing a plain char that happens to be negative is undefined behaviour, and it only shows up on input outside ASCII — which is to say, in production.

    Check errno only after a call has already told you it failed. It is not cleared on success, so reading it at any other moment gives you a stale code from something unrelated.

    Preprocessor

    In plain terms

    Before the compiler ever sees your file, a simpler program does a find-and-replace pass over it. #include pastes in another file; #define substitutes one piece of text for another. It does not understand C at all, which is why its mistakes produce such strange error messages.

    The preprocessor runs before the compiler and performs pure text substitution. It knows nothing about types, scope or C syntax — it is find-and-replace with conditionals. Every macro bug traces back to that one fact.

    include & define

    #include <stdio.h>    // search system dirs
#include "myheader.h" // search here first

#define MAX 100
#define SQUARE(x) ((x) * (x))   // parenthesize
#define MAX2(a,b) ((a) > (b) ? (a) : (b))
#undef MAX

    #include literally pastes the named file in at that point — which is why a header with a syntax error breaks every file that includes it, and why include order can matter.

    A #define substitutes text everywhere the name appears afterwards. No type is checked, no scope is respected; MAX is replaced even inside another function.

    Prefer const, enum and static inline where you can. They respect types and scope, and the debugger can still see them.

    Macro traps

    #define SQ(x) x * x
SQ(2 + 3)      // → 2 + 3 * 2 + 3 = 11, not 25
#define SQ(x) ((x) * (x))   // fixed

SQ(i++)        // → ((i++) * (i++)) — i moves twice

// multi-statement macros need this wrapper
#define SWAP(a,b) do { int t=(a); (a)=(b); (b)=t; } while (0)

    Because substitution is textual, the argument's own operators land in the middle of your expression and get regrouped by precedence. Wrapping every parameter and the whole body in parentheses is the only defence.

    Parentheses can't fix double evaluation, though — the argument text appears twice, so any side effect happens twice. That's why MAX2(i++, j) is a bug no amount of brackets will save.

    The do { } while (0) wrapper makes a multi-statement macro behave as a single statement, so it survives being used as the body of a brace-less if.

    Include guards

    #ifndef MYHEADER_H
#define MYHEADER_H

// ... declarations ...

#endif /* MYHEADER_H */

// or, non-standard but universally supported:
#pragma once

    Headers include other headers, so the same file easily arrives twice in one translation unit — and redefining a struct or typedef is an error. The guard means: if this symbol is already defined we've been here, so skip to #endif.

    Every header needs one. Give each a name derived from the filename so two headers can't collide.

    Name the guard after the file's path, not the file alone. Two headers called util.h in different directories with the same guard means the second one silently vanishes.

    Conditional compilation

    #ifdef DEBUG
    printf("state = %d\n", state);
#endif

#if defined(_WIN32)
    #include <windows.h>
#elif defined(__linux__)
    #include <unistd.h>
#else
    #error "Unsupported platform"
#endif

// define from the command line:  gcc -DDEBUG prog.c

    Code inside a false branch is deleted before the compiler ever sees it, so it costs nothing at runtime and doesn't even need to compile on other platforms. That's how one source file supports Windows and Linux.

    The flip side: unbuilt branches are unchecked branches. Code hidden behind an inactive #ifdef silently rots, and you find out when someone enables it.

    Code inside a disabled branch is never compiled, so it is never checked. A platform you do not build for will accumulate errors quietly — which is why cross-compiling early is worth the setup.

    # and ## and predefined macros

    #define STR(x)  #x            // stringify: hello → "hello"
#define CAT(a,b) a##b         // paste: my,Var → myVar

__FILE__  __LINE__  __func__  __DATE__  __TIME__

#define LOG(fmt, ...) \
    fprintf(stderr, "%s:%d: " fmt "\n", \
            __FILE__, __LINE__, __VA_ARGS__)

    # wraps an argument's text in quotes and ## glues two tokens into one — both only possible because macros work on text. Together they build logging and testing frameworks.

    The LOG macro shows why: __FILE__ and __LINE__ expand at the call site, so every message reports where it actually came from. A function couldn't do that.

    A trailing backslash continues a macro onto the next line, and nothing may follow it — not even a single trailing space.

    Seeing what it actually produced

    gcc -E prog.c | less     // stop after preprocessing
gcc -dM -E - < /dev/null // list every predefined macro

    Macro errors produce baffling messages because the compiler reports on text you never wrote. -E shows the expanded source, which usually makes the problem obvious in seconds.

    gcc -E is the first move on any macro error, not the last. The message describes text you never wrote, so looking at the text the compiler actually saw usually ends the search immediately.

    Bit manipulation

    In plain terms

    A number is stored as a row of 1s and 0s. These operators read and change individual positions in that row, so a single integer can carry 32 separate yes/no answers. Everywhere in systems and kernel code, rare in ordinary programs.

    One 32-bit integer can hold 32 independent yes/no answers, and the bitwise operators let you set, clear and test them without touching the others. Use unsigned types throughout — signed shifting wanders into undefined behaviour quickly.

    The four operations

    x |=  (1u << n);   // SET bit n to 1
x &= ~(1u << n);   // CLEAR bit n to 0
x ^=  (1u << n);   // TOGGLE bit n
(x >> n) & 1u      // TEST bit n → 0 or 1

#define READ  (1u << 0)
#define WRITE (1u << 1)
#define EXEC  (1u << 2)

unsigned perms = READ | WRITE;
if (perms & WRITE) puts("writable");
perms &= ~WRITE;               // revoke

    All four follow from one idea: 1u << n builds a mask with a single 1 in position n. OR with it and that bit turns on while the rest are untouched (x|0 leaves x alone). AND with the inverted mask and that bit turns off while the rest survive (x&1 leaves x alone). XOR flips it.

    Testing gives a non-zero value, not necessarily 1 — perms & WRITE yields 2 here. Fine in an if, wrong if you compare it to 1.

    Write 1u, not 1. Shifting a signed 1 into the top bit is undefined behaviour, and it is the single most common defect in otherwise correct bit code.

    Useful tricks

    x & 1                // is x odd?
x & (x - 1)          // clears the lowest set bit
!(x & (x - 1))       // is x a power of two? (x != 0)
x & -x               // isolates the lowest set bit

x << n               // x * 2ⁿ
x >> n               // x / 2ⁿ  (unsigned)

int count = 0;                          // popcount
for (unsigned v = x; v; v &= v - 1) count++;

    The key identity: subtracting 1 flips the lowest set bit to 0 and turns every zero below it into a 1. ANDing that back with x therefore erases exactly one bit — so the loop runs once per set bit rather than 32 times.

    A power of two has exactly one bit set, so clearing it leaves zero. GCC and Clang also offer __builtin_popcount, which compiles to a single instruction.

    x & (x - 1) clears the lowest set bit, and x & -x isolates it. Those two identities are behind most of the bit tricks you will see in other people's code.

    Packing and extracting fields

    #define FIELD(x, hi, lo) \
    (((x) >> (lo)) & ((1u << ((hi) - (lo) + 1)) - 1))

uint32_t rgb = (r << 16) | (g << 8) | b;   // pack
uint8_t  red = (rgb >> 16) & 0xFF;         // unpack

for (int i = 7; i >= 0; i--)               // print a byte
    putchar((byte >> i) & 1 ? '1' : '0');

    Extracting is always the same two steps: shift the field down to position 0, then mask off everything above it. (1u << w) - 1 builds a mask of w ones, since one-more-than-a-power-of-two minus one is all ones below.

    Packing reverses it — shift each value into its slot and OR them together. This is how colours, IP headers and instruction encodings are laid out, and unlike bit fields the layout is exactly what you wrote.

    Write the field layout down in a comment above the code — which bits, in which order, totalling how many. Every packing bug is a disagreement between the packer and the extractor about that layout.

    Shift rules that bite

    • Shifting by an amount ≥ the type's width is undefined, not zero. 1u << 32 on a 32-bit int is a bug, and on x86 it often produces 1.
    • 1 << 31 overflows a signed int. Write 1u << 31.
    • Right-shifting a negative signed value is implementation-defined — usually sign-extending, but don't rely on it.
    • Operands narrower than int are promoted first, so uint8_t x = 0xFF; ~x is 0xFFFFFF00, not 0.

    Gotchas & undefined behaviour

    In plain terms

    Some mistakes in C are not errors that stop your program. The language declines to say what should happen at all, and the compiler is then allowed to assume you never made the mistake. That is why this class of bug works on your machine, works for a year, and then breaks when you change an unrelated line.

    Undefined behaviour does not mean "crashes". It means the standard imposes no requirements at all, so the compiler may assume it never happens and optimise on that assumption. This is why UB bugs appear when you add -O2, or only on the other machine, or only for the customer. The tools at the bottom of this section find them faster than reading ever will.

    = instead of ==

    if (x = 5) { ... }    // assigns 5, result is 5 → true
if (x == 5) { ... }   // compares

if (5 == x) { ... }   // "Yoda": a typo won't compile

    Assignment is an expression whose value is the value assigned, so if (x = 5) is always true and quietly destroys x. It's legal C — genuinely useful in while ((c = getchar()) != EOF) — which is why it can't simply be banned.

    -Wall warns unless you add extra parentheses, which is the conventional way to say "I meant this".

    Off-by-one and bounds

    int a[5];
for (int i = 0; i <= 5; i++) a[i] = 0;  // writes a[5]
for (int i = 0; i <  5; i++) a[i] = 0;  // correct

char buf[5];
strcpy(buf, "hello");   // needs 6 bytes: 5 + '\0'

    Valid indices are 0 to n-1, so a correct loop uses <, never <=. Nothing checks this at runtime — writing a[5] just modifies whatever those four bytes happen to be, often another local variable.

    Strings need one extra byte for the terminator that strlen doesn't count. Almost every buffer-size bug in C is this +1.

    Returning a local's address

    char *name(void) {
    char buf[32] = "Ada";
    return buf;            // buf dies at this line
}

void name_into(char *out, size_t n) {   // caller owns
    snprintf(out, n, "Ada");            // the buffer
}

    The array lived in this function's stack frame, and the frame is released on return. The pointer still holds a valid-looking address, and the data is often still readable — until the next function call overwrites that region with its own locals.

    Three real fixes: malloc it and document that the caller frees, take a caller-supplied buffer as above, or return a pointer to something static or literal. The middle option is the most common in good C APIs.

    Uninitialized memory

    int x;
printf("%d", x);        // garbage, and UB

int *p;
*p = 5;                 // writes to a random address

int *q = malloc(4);     // malloc does NOT zero
printf("%d", *q);       // garbage; use calloc

    Uninitialized locals hold whatever the last function left on the stack, which makes them accidentally stable — the value is often 0 in debug builds and something else entirely with optimization on. That's a bug that "only happens in release".

    An uninitialized pointer is far worse than an uninitialized int: dereferencing it writes to an arbitrary address, which may corrupt live data rather than crashing.

    int x = 0; and int *p = NULL; at declaration. It costs nothing and eliminates this whole category.

    Dangling pointers & double free

    free(p);
printf("%d", *p);   // use-after-free
free(p);            // double free → heap corruption

free(p);
p = NULL;           // free(NULL) is legal and does nothing,
                    // so this makes both lines above safe

int *r = malloc(10 * sizeof *r);
r++;
free(r);            // invalid — not the original address

    free hands the block back to the allocator but doesn't change your pointer, which still points at memory that is no longer yours. Reading it usually returns the old contents — right up until malloc reissues that block to someone else.

    Setting the pointer to NULL afterwards converts both failure modes into an immediate, obvious crash — or into nothing at all, since freeing NULL is defined as a no-op.

    free must receive exactly the address malloc returned. Walk the pointer forward and you must walk it back, or keep a separate copy.

    sizeof on a parameter

    void f(int arr[]) {
    size_t n = sizeof arr / sizeof arr[0];  // WRONG
}   // arr is a pointer here → 8 / 4 = 2

void f(int arr[], size_t n) { ... }   // pass the length

void g(char *s) { sizeof s; }   // 8, not the length
                                // use strlen(s)

    The int arr[] syntax is a comfortable lie — the parameter is a pointer, and the size information was lost at the call. The idiom only works in the scope where the array was declared.

    Worse, it compiles silently and produces a plausible small number, so the loop processes two elements and everything looks almost fine.

    Comparing the wrong things

    if (str1 == str2)              // compares ADDRESSES
if (strcmp(str1, str2) == 0)   // compares text

if (0.1 + 0.2 == 0.3)          // false — binary floats
if (fabs(a - b) < 1e-9)        // use a tolerance

if (-1 < sizeof(int))          // FALSE — -1 converts to
                               // a huge unsigned value

    Each of these compiles without complaint and does something reasonable — just not what you meant. The string case is the most common: == on two char* asks whether they point at the same memory, which is occasionally true by accident when the compiler pools identical literals.

    The signed/unsigned one is the sneakiest, because sizeof returns size_t. Any comparison mixing a signed variable with a sizeof or strlen result deserves a second look.

    strncpy doesn't terminate

    char d[5];
strncpy(d, "hello", 5);   // copies 5 chars, no '\0'
puts(d);                  // reads off the end

snprintf(d, sizeof d, "%s", "hello");   // always safe

    Despite appearances, strncpy was never a safe strcpy. It was designed for fixed-width records: it pads with zeros if the source is short, and omits the terminator entirely if the source fills the buffer.

    So it silently produces an unterminated "string", and the damage shows up in whatever reads it next. Use snprintf, which always terminates and truncates cleanly.

    Sequence points

    i = i++;                      // UB
a[i] = i++;                   // UB
printf("%d %d", i++, i++);    // UB, and the argument
                              // order is unspecified too
i++;                          // just write two statements
a[i] = i;

    C leaves the order of evaluation within an expression largely to the compiler, which is what allows aggressive optimization. The price is that modifying a variable twice — or modifying and separately reading it — between sequence points is undefined.

    These are not "compiler-dependent but predictable"; the standard permits anything, and real compilers do produce different results at different optimization levels. Split the expression.

    Format string mismatches

    printf("%d\n", 3.14);      // UB — reads the wrong bytes
printf("%s\n", 42);        // UB — treats 42 as an address
printf("%d\n", (long)x);   // wrong width — use %ld
printf("%d\n", sizeof x);  // use %zu
scanf("%d", n);            // missing & — crash

    printf is variadic, so it has no idea what you actually passed. It reads bytes off the argument list according to the format string alone — and one mismatched specifier desynchronizes every argument after it.

    %s with an integer is the dangerous one: it takes 42 as an address and starts reading a string from there.

    -Wall -Wformat catches every example above at compile time. This is the single highest-value warning flag in C.

    Integer overflow & division

    int x = INT_MAX;
x + 1;              // signed overflow = UB
                    // (unsigned wraps — that IS defined)

int avg = (a + b) / 2;       // can overflow first
int avg = a + (b - a) / 2;   // safe

x / 0;              // UB — not infinity, not a crash
                    // you can rely on
int half = 7 / 2;   // 3 — integer division

    Signed overflow being undefined isn't pedantry: compilers use it to assume x + 1 > x is always true, and will delete overflow checks written that way. Check before the operation — if (a > INT_MAX - b) — rather than after.

    The midpoint bug is famously real: it sat in binary search implementations, including Java's, for years.

    Small things that bite

    • A missing break falls through to the next case, silently.
    • if (x) ; — the semicolon is the entire body.
    • char may be signed or unsigned; use unsigned char for raw bytes.
    • A leading zero makes an octal literal: 011 is 9.
    • Writing through char *s = "hi" is UB — literals are read-only.
    • getchar() returns int, because EOF doesn't fit in a char.
    • Declaring a variable in a case needs its own { }.
    • Mixing int and size_t in a comparison converts the int to unsigned.

    Multi-file projects & building

    In plain terms

    Once a program is more than one file, two separate things happen: each file is compiled on its own, and then a linker stitches the results into one program. Most baffling error messages come from not knowing which of those two steps failed.

    The compiler sees one .c file at a time and knows nothing about the others; the linker joins the results afterwards. Headers exist to tell each file what exists elsewhere. Almost every confusing build error comes from that split.

    Splitting a program

    /* math_utils.h — WHAT exists */
#ifndef MATH_UTILS_H
#define MATH_UTILS_H
int add(int a, int b);
extern int call_count;      // declaration only
#endif

/* math_utils.c — HOW it works */
#include "math_utils.h"
int call_count = 0;                     // the definition
static int helper(int x) { return x; }  // file-private
int add(int a, int b) { call_count++; return a + b; }

    The header is the public interface: declarations, typedefs, structs and macros. The .c file holds the implementation. Change the implementation and nothing else needs recompiling; change the header and everything that includes it does.

    Mark helpers static to keep them out of the global namespace — otherwise two files with a helper() each collide at link time.

    Never define a variable in a header. Every file that includes it gets its own definition and the linker reports a duplicate. Declare it extern in the header, define it in exactly one .c.

    Compiling & linking

    # all at once
gcc -Wall -Wextra -g main.c math_utils.c -o app

# separately — only rebuild what changed
gcc -c main.c        # → main.o
gcc -c math_utils.c  # → math_utils.o
gcc main.o math_utils.o -o app

-I dir     # extra header search path
-L dir -lm # library path, and link libm
-O2        # optimize

    Two distinct phases. Compiling turns each .c into an object file full of machine code with holes where calls to other files go. Linking fills the holes and produces the executable.

    Knowing which phase failed tells you where to look: compile errors are syntax and type problems in one file, link errors are about names that are missing or duplicated across files.

    Read the message for ld or collect2. Their presence means the compile step already succeeded and the problem is a definition that does not exist — a completely different search from a syntax error.

    A minimal Makefile

    CC     = gcc
CFLAGS = -Wall -Wextra -g -std=c11
OBJS   = main.o math_utils.o

app: $(OBJS)
	$(CC) $(OBJS) -o app

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f $(OBJS) app

    Each rule reads "target: things it depends on", followed by the command to build it. make compares timestamps and rebuilds only what's out of date, which is why large C projects rebuild in seconds.

    $< is the first prerequisite and $@ is the target, so the pattern rule handles every .c file.

    Recipe lines must begin with a real tab. Spaces produce "missing separator", the most confusing error message in the toolchain.

    Linker errors, decoded

    • undefined reference to `foo' — something calls foo but no object file defines it. You declared it and forgot to write it, forgot to pass that .c to the compiler, or forgot a library flag such as -lm.
    • multiple definition of `x' — two object files both define it. Usually a variable defined in a header. Use extern there and define it once in a .c.
    • implicit declaration of function — a compiler-stage error: you called something with no declaration in scope. Missing #include, or a typo in the name.

    undefined reference means declared but never defined; multiple definition means defined in a header that got included twice. The first wants a file added to the build, the second wants static or extern.

    Debugging tools

    # catch memory bugs as they happen
gcc -fsanitize=address,undefined -g prog.c -o prog

# find leaks and uninitialized reads
valgrind --leak-check=full --track-origins=yes ./prog

gdb ./prog
  break main        # or  break file.c:42
  run
  next / step       # step over / into
  print x
  backtrace         # how did I get here

    AddressSanitizer instruments your program so an out-of-bounds write or use-after-free reports at the exact line it happens, instead of crashing somewhere unrelated later. It costs roughly 2× runtime and is worth it on every debug build.

    When a program does crash, gdb's backtrace shows the chain of calls that led there — usually enough to identify the bug without a single printf.

    Keep -g -fsanitize=address,undefined in your default build line and take it out only when you measure. The 2× runtime is irrelevant on anything you are still writing.

    Habits that prevent most C bugs

    • Compile with -Wall -Wextra and fix every warning, not just the ones you understand.
    • Initialize every variable where you declare it.
    • Check the return of malloc, fopen, scanf — the three that fail quietly.
    • Set pointers to NULL immediately after free.
    • Prefer the bounded functions: snprintf, fgets, strncat.
    • Pass array lengths alongside array pointers, every time.
    • Run the sanitizers before you believe the program works.
    • Free in the reverse order you allocated, and give each allocation one clear owner.

    The highest-value one on this list is treating warnings as errors from the very first program. A warning you have learned to scroll past is a warning that is not doing anything.

    Common data structures

    In plain terms

    A data structure is a decided-on way to arrange values in memory so that one particular question becomes cheap to answer. An array makes “give me item 500” instant. A hash map makes “is this name in here?” instant. You choose by which question you will ask most. C ships none of them, so these are the four you end up writing yourself.

    C ships no containers at all. Every project ends up with some version of these four, so it is worth knowing the shape of each well enough to write it without looking — and knowing which one the problem actually wants.

    Dynamic array — the default choice

    typedef struct { int *data; size_t len, cap; } Vec;

bool vec_push(Vec *v, int x) {
    if (v->len == v->cap) {
        size_t n = v->cap ? v->cap * 2 : 4;
        int *t = realloc(v->data, n * sizeof *t);
        // never assign realloc's result straight to v->data
        if (!t) return false;
        v->data = t; v->cap = n;
    }
    v->data[v->len++] = x;
    return true;
}

    Doubling rather than incrementing is what makes n appends cost O(n) overall instead of O(n²). The array is contiguous, so iteration is cache-friendly — usually beating a linked list even where the theory says otherwise.

    Design the all-zeroes value to be a valid empty container. Vec v = {0}; then needs no init call, and there is no uninitialised-use bug to have.

    Hash map — chaining

    typedef struct Entry {
    char *key; int val; struct Entry *next;
} Entry;

Entry *buckets[16];

size_t hash(const char *s) {          // FNV-1a
    size_t h = 1469598103934665603UL;
    for (; *s; s++) {
        h ^= (unsigned char)*s;
        h *= 1099511628211UL;
    }
    return h % 16;
}

    Each bucket holds a linked list of entries whose keys hashed there. Lookup hashes, then walks that one short list comparing keys with strcmp — the hash narrows the search, it does not decide the answer.

    The map must own a copy of the key. Storing the caller's pointer works until someone passes a stack buffer that goes out of scope, and then the key dangles while every lookup still appears to run.

    Ring buffer — fixed-size FIFO

    typedef struct {
    int buf[CAP]; size_t head, count;
} Ring;

bool push(Ring *r, int v) {
    if (r->count == CAP) return false;
    r->buf[(r->head + r->count) % CAP] = v;
    r->count++;
    return true;
}
bool pop(Ring *r, int *out) {
    if (r->count == 0) return false;
    *out = r->buf[r->head];
    r->head = (r->head + 1) % CAP;
    r->count--;
    return true;
}

    One allocation, no allocation at all after setup, and constant-time push and pop. This is the structure behind audio buffers, log ring buffers and the kernel's printk buffer.

    Keeping a count is what makes full distinguishable from empty. With only head and tail indices, both states read as head == tail, and the usual workaround is to waste one slot.

    Which one, actually

    • Dynamic array — the default. Index access, tight iteration, one allocation. Insertion in the middle costs a memmove.
    • Linked list — only when you splice or remove from the middle constantly and hold the node already. Pointer chasing wrecks cache locality.
    • Hash map — keyed lookup where the key is not a small integer. Costs a hash and an allocation per entry.
    • Ring buffer — bounded producer/consumer where dropping or blocking on full is acceptable and allocation is not.

    The honest default in C is a dynamic array with a linear scan. At a few hundred elements it usually beats the "better" structure, and it is far harder to get wrong.

    Idioms & design patterns

    In plain terms

    Other languages have built-in features for cleaning up after yourself, hiding internals, and reporting failure. C has none of them — it has conventions instead, agreed ways of writing things that nearly every C codebase follows. Learn the four here and unfamiliar C stops looking arbitrary.

    C has no classes, no destructors and no exceptions. What it has instead is four conventions that between them cover most of what those features do — and every large C codebase uses all four.

    Function pointers and callbacks

    typedef int (*binop)(int, int);

static const struct {
    const char *name;
    binop fn;
} TABLE[] = {
    { "add", op_add },
    { "mul", op_mul },
};

// dispatch by name, no switch to update
for (size_t i = 0; i < LEN(TABLE); i++)
    if (!strcmp(name, TABLE[i].name))
        return TABLE[i].fn(a, b);

    This is C's polymorphism. Adding an operation means adding one table row rather than editing a switch that lives somewhere else, so the thing you add and the thing you change are the same line.

    Mark the table const so it lands in read-only memory. A stray write then traps instead of quietly redirecting a function call — which is the difference between a crash and a security bug.

    Opaque pointers — C's private fields

    // widget.h — the caller sees only this
typedef struct Widget Widget;
Widget *widget_create(int size);
void    widget_destroy(Widget *w);
int     widget_size(const Widget *w);

// widget.c — the definition lives here alone
struct Widget { int size; char *buf; };

    Because the header never defines the struct body, callers cannot read or write fields, cannot allocate one on the stack, and cannot depend on its layout. You can reorder or rename every field without recompiling a single caller.

    The cost is that every instance must be heap-allocated and reached through the API. That is usually a fair price for an interface you can change later.

    The one good goto: unified cleanup

    int load(const char *path) {
    FILE *f = NULL;
    char *buf = NULL;
    int rc = -1;

    f = fopen(path, "rb");
    if (!f) goto out;

    buf = malloc(SIZE);
    if (!buf) goto out_close;

    if (fread(buf, 1, SIZE, f) != SIZE) goto out_free;

    rc = 0;                    // success

out_free:  free(buf);
out_close: fclose(f);
out:       return rc;
}

    Each label undoes exactly one acquisition, and control enters the ladder at the point matching how far setup got. No cleanup is duplicated across branches, and adding a fifth resource means adding one label, not editing five error paths.

    This is the dominant error-handling shape in the Linux kernel. Nested ifs achieve the same thing at four levels of indentation and duplicate every free.

    Object-oriented C

    struct shape_ops {
    double (*area)(const void *self);
    void   (*print)(const void *self);
};

typedef struct {
    const struct shape_ops *ops;   // vtable, first member
    double r;
} Circle;

// call through the vtable
s->ops->area(s);

    A struct of function pointers is a vtable; putting it first means a pointer to the object is also a pointer to its operations. This is exactly what struct file_operations is in the kernel, and how one read() call reaches a different function per filesystem.

    Inheritance is done by embedding the base struct as the first member, so a pointer to the derived type is validly a pointer to the base. That guarantee is in the standard; relying on any other field's offset is not.

    0x11

    Concurrency

    In plain terms

    Concurrency is doing more than one thing at a time inside a single program. Threads make that fast because they all see the same memory — and dangerous for exactly the same reason: two threads touching one value at the same moment can leave it holding something neither of them wrote.

    Threads share one address space, which is what makes them fast and what makes them dangerous. Everything here exists to answer one question: which thread may touch this memory, and when.

    Create and join

    #include <pthread.h>

void *worker(void *arg) {
    Job *j = arg;
    j->result = compute(j->input);
    return NULL;
}

pthread_t t;
pthread_create(&t, NULL, worker, &job);
// ... other work ...
pthread_join(t, NULL);   // now job.result is safe to read

// compile with -pthread, not -lpthread

    The thread function takes and returns void *, so anything richer travels in a struct you own. pthread_join both waits and establishes that everything the thread wrote is visible to you afterwards.

    Reading a worker's output before joining is a data race even if the worker has certainly finished. The join is what makes the write visible, not the passage of time.

    Mutexes

    static pthread_mutex_t lock =
    PTHREAD_MUTEX_INITIALIZER;
static long counter = 0;

pthread_mutex_lock(&lock);
counter++;              // read, add, write — three steps
pthread_mutex_unlock(&lock);

    counter++ is not one operation. Two threads can both read 5, both compute 6, and both store 6 — one increment vanishes. The mutex makes the three steps indivisible with respect to other threads holding the same lock.

    Always take multiple locks in the same global order. Two threads taking A then B, and B then A, is the textbook deadlock and it appears only under load.

    Condition variables

    pthread_mutex_lock(&m);
while (queue_empty(&q))          // while, never if
    pthread_cond_wait(&cv, &m);
item = queue_pop(&q);
pthread_mutex_unlock(&m);

// producer side
pthread_mutex_lock(&m);
queue_push(&q, item);
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);

    pthread_cond_wait atomically releases the mutex and sleeps, then reacquires it before returning. That atomicity is the whole point — checking a condition and sleeping in two separate steps loses wakeups that land in between.

    The while is mandatory. Spurious wakeups are permitted by the standard, and a signal may also be consumed by a different waiter, so the condition must be rechecked after every wake.

    Atomics, and finding races

    #include <stdatomic.h>
_Atomic long counter = 0;
counter++;              // now indivisible, no lock

atomic_fetch_add(&counter, 1);
atomic_load(&flag);

# the only reliable way to find a race
gcc -fsanitize=thread -g prog.c -pthread

    An _Atomic object is safe to touch from several threads without a mutex, and for a single counter it is faster. It does not extend to two variables that must agree — that still needs a lock.

    ThreadSanitizer reports races that did not manifest on that run, which is the only way to test for them. A race that produced the right answer ten thousand times is still a bug and will surface on different hardware.

    0x12

    Processes, IPC & signals

    In plain terms

    A process is a whole separate running program with its own memory. This is how your program starts another one, passes data to it, and reacts to interruptions from outside. It is the machinery a shell is built out of.

    Where threads share memory, processes share nothing and must be told how to talk. This is the layer the shell is built out of, and the first place C stops being portable and starts being POSIX.

    fork, exec, wait

    pid_t pid = fork();
if (pid == -1)      { perror("fork"); }
else if (pid == 0)  {
    execlp("ls", "ls", "-l", (char *)NULL);
    _exit(127);          // only reached if exec failed
} else {
    int status;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status))
        printf("%d\n", WEXITSTATUS(status));
}

    fork returns twice: 0 in the child, the child's PID in the parent. exec replaces the current program image entirely and never returns on success — which is why the line after it is an error path.

    A child that is never waited for becomes a zombie holding a process-table slot. waitpid is not optional bookkeeping.

    Pipes

    int fd[2];
pipe(fd);              // fd[0] read, fd[1] write

if (fork() == 0) {
    close(fd[0]);      // child writes
    write(fd[1], msg, len);
    close(fd[1]);
    _exit(0);
}
close(fd[1]);          // parent MUST close its write end
while ((n = read(fd[0], buf, sizeof buf)) > 0)
    fwrite(buf, 1, n, stdout);

    A pipe is a one-way byte stream with a small kernel buffer. read returns 0 — end of file — only once every copy of the write end is closed, and fork duplicated them all.

    Forgetting to close the unused end in the parent is the classic pipe hang: the reader waits forever for an EOF that its own open descriptor is preventing.

    Signals

    static volatile sig_atomic_t stop = 0;

static void on_sigint(int sig) {
    (void)sig;
    stop = 1;          // the only safe kind of work
}

struct sigaction sa = {0};
sa.sa_handler = on_sigint;
sigaction(SIGINT, &sa, NULL);

while (!stop) { /* work */ }

    A handler runs by interrupting whatever the program was doing, possibly mid-malloc. Only async-signal-safe functions may be called from one, and printf and malloc are emphatically not on that list.

    Set a volatile sig_atomic_t flag and handle it in the main loop. volatile stops the compiler caching the flag in a register across the loop, which would make the exit condition unreachable.

    Other IPC, in one line each

    • Named pipe (FIFO) — mkfifo. A pipe with a filesystem name, so unrelated processes can meet.
    • Unix domain socket — bidirectional, can pass file descriptors between processes. The general answer.
    • Shared memory — shm_open + mmap. Fastest, and you supply your own locking.
    • Message queue / semaphore — POSIX mq_* and sem_*. Structured, less common in new code.

    Everything here is POSIX, not ISO C. It exists on Linux and macOS and not on Windows, which has an entirely separate API for the same jobs.

    0x13

    Testing

    In plain terms

    A test is a small program that runs your code on a known input and checks the answer, so that when you change something later you find out immediately if you broke it. C has no test runner built in — you write a second program and compare.

    C has no built-in test runner, so testing is a convention rather than a feature. The bar worth clearing is low and pays immediately: a second binary that exercises your functions and returns non-zero when something is wrong.

    assert, and what belongs in one

    #include <assert.h>

void *dup_n(const void *src, size_t n) {
    assert(src != NULL);       // a bug if violated
    ...
}

// compiled out entirely with -DNDEBUG
gcc -DNDEBUG -O2 prog.c

    An assert documents something that must be true if the code is correct. It is for programmer errors — a null argument, a broken invariant — never for runtime conditions like a missing file or bad user input, which must be handled rather than asserted.

    Never put a side effect inside an assert. assert(pop(&q) == 3) stops popping entirely under -DNDEBUG, and the release build then behaves differently from the one you tested.

    A test runner in fifteen lines

    static int failures = 0;

#define CHECK(cond) do {                       \
    if (!(cond)) {                             \
        printf("FAIL %s:%d  %s\n",             \
               __FILE__, __LINE__, #cond);     \
        failures++;                            \
    }                                          \
} while (0)

int main(void) {
    CHECK(my_strlen("abc") == 3);
    CHECK(my_strlen("") == 0);
    printf("%d failures\n", failures);
    return failures != 0;
}

    #cond stringifies the expression so the failure prints the actual test, and __FILE__/__LINE__ locate it. Returning non-zero is what lets make test or CI notice.

    The do { ... } while (0) wrapper makes the macro behave like a single statement, so it is safe after an if with no braces. Every multi-statement macro needs it.

    The frameworks worth knowing

    • Unity — one C file and one header, drop it in. The usual choice for embedded work.
    • CMocka — adds mocking and per-test process isolation, so a segfault in one test does not lose the whole run.
    • Check — forks each test for the same reason; long-standing and well documented.
    • greatest / µnit — single-header, minimal, no build integration needed.

    All four solve the same problem. Pick the one your project's build system already supports rather than the one with the best feature list.

    Sanitizers are part of testing

    # run the suite three times, differently
gcc -fsanitize=address,undefined -g test.c
gcc -fsanitize=thread -g test.c -pthread
valgrind --leak-check=full ./test

# and check what the tests actually reached
gcc --coverage test.c && ./a.out && gcov test.c

    A passing test suite in C proves much less than in a memory-safe language: the code can be corrupting the heap and still print the right answers. Running the same tests under a sanitizer is what converts "the output looked right" into evidence.

    ASan and TSan cannot be combined in one binary. Two builds of the same tests is the standard arrangement.

    Build systems & tooling

    In plain terms

    A build system is a file describing how to turn your source into a working program, so you type one command instead of twelve. make is the traditional one; the newer tools exist because make becomes unwieldy across many directories and machines.

    Make is enough for one directory. Past that, the questions are dependency discovery, cross-compilation and generating project files for other people's editors — which is where the newer tools earn their complexity.

    CMake — the de facto standard

    cmake_minimum_required(VERSION 3.16)
project(app C)
set(CMAKE_C_STANDARD 11)

add_executable(app main.c util.c)
target_compile_options(app PRIVATE
    -Wall -Wextra)
target_link_libraries(app m)
    cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j
ctest --test-dir build

    CMake generates a build rather than performing one — Makefiles, Ninja files, or an IDE project from the same input. That indirection is the reason it handles cross-compilation and dependency discovery that a hand-written Makefile cannot.

    Always build out of tree (-B build). An in-source build scatters generated files through your repository and there is no clean way to undo it.

    Ninja and Meson

    # meson.build
project('app', 'c',
        default_options: ['c_std=c11'])
executable('app', 'main.c', 'util.c')

# build
meson setup build
ninja -C build

    Ninja is deliberately not written by hand — it is a fast low-level executor that CMake and Meson generate. Meson is a higher-level configuration language that is markedly more readable than CMake's, and is what GNOME, systemd and Mesa use.

    Adding -G Ninja to a CMake invocation usually halves incremental build time and changes nothing else.

    Compiler flags worth knowing

    -Wall -Wextra        // the baseline, always
-Wpedantic           // strict ISO conformance
-Wshadow             // a local hiding an outer name
-Wconversion         // silent narrowing
-Werror              // warnings become errors (CI)

-O0 -g               // debug builds
-O2                  // the sane release default
-Og                  // optimised but still debuggable
-march=native        // this machine only, not for release

-fsanitize=address,undefined
-D_FORTIFY_SOURCE=2  // cheap runtime bounds checks

    -O2 is where undefined behaviour starts to bite: the optimiser assumes UB never happens and deletes code that only made sense if it did. Code that works at -O0 and breaks at -O2 is almost always UB, not a compiler bug.

    -Wconversion is noisy on existing code and worth switching on for anything new. Silent narrowing is a whole bug family that nothing else catches.

    The rest of the toolbox

    • clang-format — mechanical formatting from a config file. Ends style arguments permanently.
    • clang-tidy — static analysis well beyond compiler warnings; catches many real bugs.
    • cppcheck — a second analyser with different blind spots; cheap to also run.
    • compile_commands.json — emitted by cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON; what every editor's C language server actually reads.
    • vcpkg / Conan — dependency managers. C has no standard one, which is why vendoring a library into your tree is still common and respectable.

    Run clang-tidy once on anything you are about to show someone. It catches a class of real bug that -Wall -Wextra does not, and unlike a formatter its complaints are worth reading rather than applying blindly.

    C standards

    In plain terms

    C has been revised several times since 1989 and each revision added features. Which version you compile against decides what exists and what the compiler warns about. State it explicitly, because the compiler's own default has changed between releases.

    Which standard you target decides which features exist and which warnings appear. Pass it explicitly — the compiler's default has changed over versions, and a project that never says which C it is written in eventually finds out the hard way.

    What each one added

    • C89 / C90 — the original. Declarations only at the top of a block, no // comments. Still the baseline for maximum portability.
    • C99 — // comments, declare-anywhere, stdint.h, stdbool.h, designated initialisers, VLAs, inline, long long, compound literals.
    • C11 — _Static_assert, _Atomic, threads, anonymous structs and unions, _Generic. VLAs became optional.
    • C17 / C18 — no new features; defect fixes to C11. The safe modern default.
    • C23 — true/false/bool as keywords, nullptr, typeof, binary literals, constexpr, attributes.

    -std=c11 or -std=c17 is the right default for new work. -std=gnu11 is the same plus GNU extensions, and is what most Linux projects actually use.

    Three flavours of "unpredictable"

    // undefined — anything may happen,
// including deleting surrounding code
int a[5]; a[7] = 1;
i = i++ + 1;

// unspecified — one of several valid
// outcomes, no requirement to be consistent
f(g(), h());        // evaluation order

// implementation-defined — the compiler
// must document its choice
sizeof(int);
(char)200;          // signed char or not

    Only the first is dangerous in the "optimiser deletes your bounds check" sense. Undefined behaviour is not a runtime hazard — it is a compile-time licence for the compiler to assume the case cannot arise.

    If a program has undefined behaviour anywhere, no part of its output is guaranteed, including the parts that ran before it. There is no such thing as locally contained UB.

    Why the kernel is not ISO C

    // GNU extensions the kernel depends on
typeof(x) tmp = (x);        // now C23, long a GNU ext
({ int t = a; t * t; })     // statement expressions
__attribute__((packed))
__builtin_expect(x, 1)      // likely()/unlikely()
struct { int a; char b[]; } // flexible arrays

    Linux builds as -std=gnu11 with -fno-strict-aliasing and a long list of other flags. Macros like container_of and min() are written with statement expressions and typeof so they evaluate their arguments exactly once and stay type-safe.

    Reading kernel source with only ISO C in mind will leave you puzzled by constructs that are perfectly ordinary GNU C. The extensions are documented and deliberate, not accidents.

    Feature test macros

    // must come before every #include
#define _POSIX_C_SOURCE 200809L
#include <unistd.h>

#define _GNU_SOURCE     // GNU extras: strdup on old libc,
#include <string.h>     // asprintf, memmem, ...

    Under a strict -std=c11, glibc hides everything that is not ISO C — so strdup or fileno suddenly produce implicit-declaration errors. The feature test macro asks for them back.

    It must be defined before the first #include, not after. Defining it halfway down the file is the source of the "it works in one file and not another" version of this bug.

    0x16

    Kernel C

    In plain terms

    The Linux kernel is written in C, but not the C in the rest of this file: no standard library, no floating point, and different names for nearly everything. None of it is harder than what came before — it is unfamiliar, and it is the vocabulary your first patch needs.

    The kernel is C with the standard library removed and a different set of rules put in its place. None of it is harder than what came before — it is just unfamiliar, and it is what the first file you open will be full of.

    What is missing

    • No libc. No printf, malloc, strcpy as you know them. printk, kmalloc, and kernel versions of the string functions instead.
    • No floating point. The FPU state is not saved across kernel entry. Use fixed-point arithmetic.
    • A tiny stack. Typically 8 KB or 16 KB for the whole call chain — no large local arrays, no deep recursion.
    • No memory protection. A bad pointer corrupts the kernel rather than crashing one process.
    • Concurrency everywhere. Your code can be preempted and can run simultaneously on every core.

    A userspace bug loses a process. The same bug in kernel context can corrupt a filesystem. This is why the review culture on the mailing lists is as demanding as it is.

    container_of and intrusive lists

    #define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

struct list_head { struct list_head *next, *prev; };

struct my_item {
    int value;
    struct list_head list;   // embedded, not a pointer
};

list_for_each(pos, &head) {
    struct my_item *it =
        container_of(pos, struct my_item, list);
    ...
}

    The list node lives inside the object rather than pointing at it, so adding to a list needs no allocation and cannot fail. One object can sit on several lists by embedding several list_head fields.

    The head is a sentinel and the list is circular, so no operation needs an empty-list special case. That is why the kernel's list code has almost no branches.

    Error pointers

    struct foo *make_foo(void) {
    struct foo *f = kmalloc(sizeof *f, GFP_KERNEL);
    if (!f)
        return ERR_PTR(-ENOMEM);
    ...
    return f;
}

// caller
f = make_foo();
if (IS_ERR(f))
    return PTR_ERR(f);      // a negative errno

    The top page of address space is never a valid pointer, so a small negative number encoded there is unambiguously an error. This returns a pointer or a reason in one value, without an out-parameter.

    Kernel functions return 0 on success and a negative errno on failure — -ENOMEM, -EINVAL. Returning 1 for success will be the first thing a reviewer flags.

    Allocation and locking context

    kmalloc(size, GFP_KERNEL);  // may sleep
kmalloc(size, GFP_ATOMIC);  // must not sleep
kfree(p);

// which lock depends on context
mutex_lock(&m);       // may sleep; process context
spin_lock(&l);        // never sleeps; any context
spin_lock_irqsave(&l, flags);

    The recurring question is whether the current context is allowed to sleep. In an interrupt handler or while holding a spinlock it is not — so GFP_KERNEL or mutex_lock there is a bug, even though both compile fine.

    Build with CONFIG_PROVE_LOCKING and CONFIG_DEBUG_ATOMIC_SLEEP. Lockdep catches inverted lock ordering and sleeping-in-atomic before they become an intermittent deadlock.

    User pointers are hostile

    long my_syscall(void __user *buf, size_t n)
{
    char kbuf[64];

    if (n > sizeof kbuf)
        return -EINVAL;
    if (copy_from_user(kbuf, buf, n))
        return -EFAULT;     // never dereference buf
    ...
}

    __user marks a pointer as coming from userspace. It may be invalid, may point into the kernel, and may be changed by another thread between your check and your use. copy_from_user is the only safe way across that boundary.

    Check the size before the copy, and validate anything you copied afterwards. Sparse (make C=1) enforces the __user annotation statically — run it before sending a patch.

    The submission process, in order

    git format-patch -1 -o out/
scripts/checkpatch.pl --strict out/0001-*.patch
scripts/get_maintainer.pl out/0001-*.patch

git send-email --to=maintainer@... \
               --cc=linux-subsys@vger.kernel.org \
               out/0001-*.patch

    Patches go to a mailing list as plain-text email — no attachments, no HTML, no pull requests. Read Documentation/process/submitting-patches.rst in full before the first one; it is the actual specification and reviewers assume you have.

    Read a month of your subsystem's archive on lore.kernel.org first. It tells you the maintainer's preferences and what has already been rejected — and a drive-by checkpatch cleanup is now usually treated as noise rather than a contribution.

    Building and booting one, without touching your own machine

    You cannot review a change to code you have never run. The loop below builds a kernel and boots it inside a virtual machine, so a broken one costs you a restarted QEMU rather than a bricked laptop.

    Configuring the build

    make defconfig        // sane defaults for this arch
make menuconfig       // curses UI, / to search
make localmodconfig   // only what THIS machine loads

make -j$(nproc)       // build, all cores

    A full defconfig build is thousands of modules and takes a long time. localmodconfig reads which modules are loaded right now and switches off everything else, which is usually the difference between forty minutes and five.

    In menuconfig, / searches and shows you the exact symbol name plus which options it depends on. That dependency list is why an option you want sometimes cannot be selected.

    Booting it under QEMU

    qemu-system-x86_64 \
  -kernel arch/x86/boot/bzImage \
  -initrd initramfs.cpio.gz \
  -append "console=ttyS0" \
  -nographic -m 512

// Ctrl-a then x to quit

    console=ttyS0 with -nographic puts the kernel's own messages in your terminal, which is where you will read every panic and every printk you add. Without it the boot happens in a window you cannot copy text out of.

    Boot an unmodified build first and keep it. A kernel that fails to boot after your patch is only informative if you know the same tree booted before it.

    Finding your way around 30 million lines

    make cscope && cscope -d   // in-tree index
make tags                  // for vim/emacs

// or, no setup at all:
// elixir.bootlin.com — every version,
// every identifier, cross-referenced

git log -p --follow drivers/foo/bar.c
git blame -L 120,160 drivers/foo/bar.c

    Grep does not scale here: a common identifier appears in thousands of files. cscope answers “who calls this” and “where is this defined” as separate questions, and elixir.bootlin.com does the same in a browser with nothing to install.

    git blame then git log on the commit it names is the fastest way to find out why a line is the way it is — and kernel commit messages are unusually good at saying so.

    The kernel's own sanitizers

    // in menuconfig, under Kernel hacking:
CONFIG_KASAN=y      // ASan, for the kernel
CONFIG_UBSAN=y      // undefined behaviour
CONFIG_KCSAN=y      // data races
CONFIG_LOCKDEP=y    // lock ordering

    These are the same tools as -fsanitize=address in userspace, compiled into the kernel. KASAN catches use-after-free and out-of-bounds; LOCKDEP catches a lock ordering that could deadlock even on a run where it did not.

    Turn them on in the VM and leave them on. They cost speed you do not care about there, and a patch that trips KASAN is one you want to find before a maintainer does.

    0x17

    Finding a bug

    In plain terms

    Two different jobs get called debugging. One is finding out where a program went wrong, which a tool does for you. The other is working out why, which only you can do. Everything here is about making the first one take seconds so you have the time for the second.

    Stage 4 asks for a failing test located with a backtrace alone, no printf added. That is a specific skill and it is worth about a week of guessing. Everything here is a real session, transcribed.

    Which tool, and when

    // it crashed, or gave a wrong number
gcc -g -fsanitize=address,undefined p.c -o p
./p          // the sanitizer names the line

// no sanitizer report, still wrong
gcc -g p.c -o p
gdb ./p      // step through and look

    Reach for the sanitizer first, always. It finds memory errors without you knowing where to look, and it names the file and line for free. The debugger is for the other kind of bug: the logic is wrong but the memory is fine.

    A crash under a sanitizer is a solved bug. A crash without one is a search.

    The ten commands that cover it

    break sum_slice   // or break file.c:42
run               // start, stop at the breakpoint
next              // one line, over calls
step              // one line, into calls
continue          // run to the next breakpoint
print n           // value of a variable
print a[0]@5      // five elements starting at a[0]
backtrace         // who called whom
frame 3           // move to a caller's frame
list              // source around here

    Abbreviations work and everyone uses them: b, r, n, s, c, p, bt, f. Pressing Enter on a blank line repeats the last command, which is what makes stepping bearable.

    print a[0]@5 is the one nobody finds on their own. It prints a run of elements, which is how you look at an array in a debugger.

    Session one — the program that prints the right answer and is still wrong

    This is the case that makes undefined behaviour worth taking seriously. The loop condition is <= where it should be <, so it reads one int past the end of the array.

    static int sum_slice(const int *a, size_t n) {
    int total = 0;
    for (size_t i = 0; i <= n; i++)     // the bug
        total += a[i];
    return total;
}

double average(const int *a, size_t n) {
    return (double)sum_slice(a, n) / (double)n;
}

int main(void) {
    int data[4] = { 10, 20, 30, 40 };
    printf("avg = %.2f\n", average(data, 4));
    return 0;
}

    Compiled with -Wall -Wextra it produces no warning at all, and running it prints the correct answer:

    $ gcc -std=c11 -Wall -Wextra -g avg.c -o avg
$ ./avg
avg = 25.00

    Ten, twenty, thirty and forty average to twenty-five. The program is reading memory it does not own and getting away with it, because whatever sat after the array happened to be zero. Now the same binary under the debugger:

    $ gdb ./avg
(gdb) break sum_slice
Breakpoint 1 at 0x1155: file avg.c, line 5.
(gdb) run

Breakpoint 1, sum_slice (a=0x7fffffffdc90, n=4) at avg.c:5
5           int total = 0;
(gdb) print n
$1 = 4
(gdb) print a[0]@5
$2 = {10, 20, 30, 40, -134512640}
(gdb) continue
avg = -33628135.00

    print a[0]@5 asks for five elements of a four-element array, and the fifth is -134512640 — whatever bytes happen to live there. The debugger lays out the stack slightly differently from a plain run, so this time the garbage is not zero, and the same program prints −33628135.00 instead of 25.00.

    One binary, two answers, one of them right by luck. This is what “works on my machine” means in C, and it is why the sanitizer is on in every command in this file.

    Session two — a crash, located without adding a single printf

    An array of strings with a NULL in it, passed to something that assumes it is a string.

    $ gdb ./crash
(gdb) run

0x00007ffff7db4b9d in ?? () from /usr/lib/libc.so.6
(gdb) backtrace
#0  0x00007ffff7db4b9d in ?? () from /usr/lib/libc.so.6
#1  0x0000555555555171 in length (s=0x0) at crash.c:4
#2  0x000055555555518b in report (name=0x0) at crash.c:7

(gdb) frame 3

    How to read that backtrace

    Frames are numbered from the crash outward. #0 is inside libc with no source, because you do not have its debug symbols — ignore it. The first frame naming one of your files is where to start, and here it is #1, length, with its argument already printed as s=0x0.

    The arguments are in the backtrace. name=0x0 at frame 2 says the null was already being passed in, so the bug is above, not here.

    Why frame 3

    print i at frame 2 fails with No symbol “i” in current context, because i is a local of main and you are standing in report. Moving to frame 3 puts you in main's scope, and then i, names[i] and the whole array are all readable.

    “No symbol in current context” almost never means the variable does not exist. It means you are in the wrong frame.

    printf debugging, honestly

    It is not shameful and everyone does it. It is the wrong first move when the program crashes, because a crash already carries a backtrace and printing your way to it is slower. It is the right move for a loop that goes wrong on the four-thousandth iteration, where stepping is hopeless.

    Print to stderr, not stdout — stdout is buffered, so a crash can eat the very line that would have told you where you were.

    When the crash is not reproducible

    ulimit -c unlimited      // allow core files
./prog                   // crashes, drops a core
gdb ./prog core          // open it after the fact

// or catch it as it happens
gdb -p $(pidof prog)

    A core file is a snapshot of the process at the moment it died. You get the same backtrace and the same print from it as you would live — useful when the crash happens once an hour.

    Distributions often route cores to systemd-coredump instead of the current directory. coredumpctl list then coredumpctl gdb is the shortcut.

    Looking it up

    In plain terms

    Every C function that exists is documented on your own machine, offline, in a program called man. It is faster than searching and it is describing the exact version you have installed rather than one from 2009. It just takes twenty minutes to learn to read.

    C's documentation is already on your machine and is better than most of what a search returns. It is also written in a house style that takes twenty minutes to learn and then never confuses you again.

    Man pages, and the section numbers

    man 3 printf     // the C library function
man 1 printf     // the shell command — different thing
man 2 open       // a system call
man 7 signal     // an overview page

man -k strdup    // search by keyword
man 3 malloc     // then press / to search inside

    The number is the section, and it matters more than it looks. 1 is shell commands, 2 is system calls the kernel provides, 3 is C library functions, 7 is overviews. Without a number you get the lowest-numbered match, which for printf is the shell command, not the function you meant.

    If a man page seems to describe the wrong thing entirely, you are in the wrong section. That is nearly always what has happened.

    How a man page is laid out

    NAME          // one line, what it does
SYNOPSIS      // the header to include, the signature
DESCRIPTION   // the long version
RETURN VALUE  // read this one. always.
ERRORS        // what errno will be set to
NOTES         // portability and gotchas
EXAMPLES      // sometimes
SEE ALSO      // the neighbouring functions

    SYNOPSIS answers “which header do I include”, which is the question that sends most beginners to a search engine. RETURN VALUE is the one people skip and should not: it tells you what failure looks like, and in C failure is a return value rather than an exception.

    Read RETURN VALUE and ERRORS before you write the call, not after it misbehaves. Half of C's error handling is knowing that a function reports failure by returning NULL, or -1, or a short count.

    What to do when you are stuck

    In order, because the order is what saves time:

    • Read the first error only. The rest are usually consequences. The decoder covers the thirteen you will actually meet.
    • Rebuild with the sanitizer on. Half of “I have no idea what is happening” becomes a file and line number.
    • Check the man page's RETURN VALUE. Especially if a call “did nothing”.
    • Shrink it. Cut the program down until it either works or is ten lines. Either outcome tells you where the bug is.
    • Then search — with the exact message text in quotes, not a paraphrase.

    Shrinking it is the step people skip and the one that works most often. A ten-line program that still misbehaves is a bug you can see.

    Sources worth trusting, offline and on

    On your machine: man, and the headers themselves — /usr/include/stdio.h is readable and is the actual truth about what your library provides.

    Worth knowing exists: cppreference for the standard library, the C standard's own wording when a portability argument comes up, and man 7 overview pages for whole topics like signal, pipe and epoll.

    Be wary of C answers older than about 2010, and of any answer using gets or casting the result of malloc. Both are reliable signals that the rest of the advice is dated too.

    Reading an error message

    In plain terms

    An error message is the compiler telling you what it could not do and where. It reads badly at first because it names the rule you broke rather than the thing you meant. The trick is to read only the first error — the rest are usually consequences of it — and to notice whether it came from the compiler, the linker, or the running program, because those are three different places to look.

    Left column is the message, near enough verbatim. Every one of these was produced by compiling or running the broken snippet it describes, on gcc 16.2.1 on this machine — build/verify_errors.py re-runs all thirteen and fails if the text stops matching.

    The messageWhat it means
     
    error: implicit declaration of function ‘printf’
  [-Wimplicit-function-declaration]
note: include ‘<stdio.h>’ or provide a declaration

    You called a function the compiler has never been told about.

    Add the #include the note names. gcc tells you which header it wants — this is one of the few messages that hands you the fix outright.

    /usr/bin/ld: prog.o: in function `main':
prog.c:(.text+0x5): undefined reference to `helper'
collect2: error: ld returned 1 exit status

    helper was declared so the compiler was satisfied, but no file ever defined it, so the linker cannot find the code.

    Either write the function body, or add the .c file that has it to the compile command. ld in the message is how you know this is the link step, not the compile step.

    error: ‘struct Point’ has no member named ‘z’

    A typo in a field name, or the struct you are thinking of is not the struct the compiler is looking at.

    Check the definition, and check you did not include an older header defining the same name.

    warning: format ‘%d’ expects argument of type ‘int’,
  but argument 2 has type ‘double’ [-Wformat=]

    The placeholder in the format string does not match the value you passed.

    Use %f for a double, %zu for a size_t, %s for a string. Only a warning by default — but the printed output will be garbage, so treat it as an error.

    error: initialization of ‘int’ from ‘char *’
  makes integer from pointer without a cast [-Wint-conversion]

    You assigned an address to something that holds a number, or the reverse.

    Usually a missing * or a missing &. Read the two types in the message — they tell you which direction the mistake went.

    error: passing argument 1 of ‘f’ from incompatible pointer type
  [-Wincompatible-pointer-types]

    A pointer to the wrong type. char * where int * was wanted, most often.

    Do not silence this with a cast. The sizes differ, so writing through the pointer would touch the wrong number of bytes.

    warning: suggest parentheses around assignment used as truth value
  [-Wparentheses]

    You wrote if (x = 1) — assignment — where you meant if (x == 1), comparison.

    Add the second =. This compiles and runs perfectly happily, which is why the warning exists and why -Wall is not optional.

    warning: array subscript 5 is above array bounds of ‘int[3]’
  [-Warray-bounds=]

    Reading past the end of an array the compiler can see the size of.

    Fix the index. Note this warning only appears with optimisation on — at -O0 with -Wall -Wextra the same line compiles silently, because the analysis that finds it only runs when optimising. Compile once at -O2 before believing a clean build.

    Segmentation fault (core dumped)

$ echo $status
139

    Your program touched memory it does not own — almost always a null or uninitialised pointer, or an index far outside an array.

    Note that the message comes from your shell, not your program: the program produced nothing at all. 139 is 128 + 11, signal 11 being SEGV. Rebuild with -g -fsanitize=address and run it again — the next entry is what you get instead.

    AddressSanitizer:DEADLYSIGNAL
ERROR: AddressSanitizer: SEGV on unknown address 0x000000000000
The signal is caused by a WRITE memory access.

    The same crash as above, with the sanitizer on. Address 0x000000000000 is a null pointer.

    The stack trace under the message names your file and line. This is why the sanitizer is worth its runtime cost: the plain crash gave you nothing at all.

    ERROR: AddressSanitizer: heap-use-after-free
READ of size 4 at 0x7b3675... thread T0
    #0 ... in main prog.c:3
freed by thread T0 here: ...
previously allocated by thread T0 here: ...

    You used memory after free gave it back.

    The report gives you three places at once: where you read, where it was freed, and where it was allocated. That triple is usually enough to see the ownership mistake without a debugger.

    ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7ba3c6...
READ of size 4 at 0x7ba3c6... thread T0

    An index outside a local array — the case the compiler could not see at compile time because the index was a variable.

    stack-buffer-overflow means a local array; heap-buffer-overflow means one from malloc. The prefix tells you where to look.

    ERROR: LeakSanitizer: detected memory leaks

Direct leak of 40 byte(s) in 1 object(s) allocated from:
    #0 ... in malloc
    #1 ... in main prog.c:2

    Memory from malloc that was never passed to free by the time the program ended.

    Not a crash and not a wrong answer — the program worked. It matters because a leak in a loop or a long-running process eventually is not survivable. The trace names the allocation site, not the place you forgot to free.

    A crash with no message is not less information than a sanitizer report — it is the same bug with the report switched off. Build with -g -fsanitize=address,undefined and the same crash names your file and line.

    Glossary

    Every term here appears somewhere in this file. The first time each one is used it links back to its entry, so you can follow it and come back rather than deciding whether to look it up. The second line of each entry is the one worth reading: it says whether the term matters to you yet.

    ABI

    The agreement about how compiled code passes arguments, returns values and lays structs out in memory.

    It is why a library compiled by one compiler can be called from code compiled by another — and why mixing 32-bit and 64-bit builds fails at the link step.

    alignment

    The rule that a value of a given size must start at an address that is a multiple of that size.

    It is the reason a struct is often bigger than the sum of its fields: the compiler inserts unused padding bytes to keep each field aligned.

    arena

    One large block of memory allocated up front, handed out in pieces, and freed all at once at the end.

    It turns hundreds of individual free calls into one, which removes a whole category of leak and double-free bugs at the cost of holding memory longer.

    atomic

    An operation that completes as a single indivisible step, so no other thread can observe it half-finished.

    Ordinary x++ is not atomic — it is a read, an add and a write, and two threads doing it at once can lose one of the increments entirely.

    buffer overflow

    Writing past the end of an array into memory that belongs to something else.

    C does not check array bounds, so this corrupts whatever happened to be next in memory. It is the single most exploited class of bug in the language's history.

    cache line

    The fixed-size chunk — usually 64 bytes — that the processor actually moves between memory and its cache.

    It is why walking an array in order is far faster than jumping around it: one fetch brings in the next several values for free.

    compiler

    The program that reads your C source and produces machine code.

    C does nothing until you run it. gcc and clang are the two you have installed, and each will sometimes catch a mistake the other misses.

    condition variable

    A way for one thread to sleep until another signals that something it was waiting for has become true.

    The alternative is a loop that checks over and over, which burns a whole processor core doing nothing.

    container

    Any structure that holds a collection of values — a list, a map, a queue.

    C ships none, which is the single largest practical difference from Python or R. Every C project builds or borrows its own.

    dangling

    A pointer still holding the address of memory that has already been freed or has gone out of scope.

    Using one is undefined behaviour, and it usually appears to work — the bytes are often still intact — until the moment something else reuses that memory.

    deadlock

    Two threads each holding a lock the other one needs, so neither can ever continue.

    The program does not crash; it stops responding, which makes it harder to diagnose than a crash would be. Always take multiple locks in the same order everywhere.

    dereference

    Following a pointer to reach the value it points at — written *p.

    The distinction between p and *p is the one thing to get solid before anything else in the pointer section makes sense.

    endian

    Which end of a multi-byte number a machine stores first.

    It only matters when bytes cross a boundary — a file, a network, another machine — and then it matters completely.

    errno

    A global variable the standard library sets to a numeric code when a call fails.

    It is only meaningful immediately after a call that reported failure; checking it at any other time reads a stale value left by something unrelated.

    file descriptor

    A small integer the operating system gives you to refer to an open file, socket or pipe.

    0, 1 and 2 are always standard input, output and error, which is what makes shell redirection possible.

    fork

    The system call that creates a near-identical copy of the running process.

    It returns twice — zero in the child, the child's id in the parent — which is the single strangest line in POSIX and the basis of how every shell runs a command.

    header guard

    The #ifndef / #define / #endif wrapper that stops a header being pasted in twice.

    Without it, including the same header through two paths redefines everything in it and the compiler reports errors in a file you did not touch.

    heap

    The region of memory you request explicitly with malloc and give back with free.

    It is the only place to put something whose size you do not know until the program runs, or that must outlive the function that created it.

    idiom

    A conventional way of writing something that the language does not enforce but every codebase follows.

    C's features are few, so its idioms carry the weight that language features carry elsewhere. Not knowing them makes ordinary code look arbitrary.

    linker

    The program that runs after the compiler and joins the separately compiled pieces into one executable.

    Knowing whether an error came from the compiler or the linker halves the search: the compiler complains about syntax and types, the linker about things that are declared but never defined.

    lvalue

    An expression that names a storage location, so it can appear on the left of an assignment.

    x is one; x + 1 is not. It is the vocabulary the compiler uses in the error message when you assign to something you cannot assign to.

    macro

    A preprocessor rule that replaces one piece of text with another before compilation.

    It has no idea about types or scope, so its arguments can be evaluated twice. That is why macro parameters get wrapped in brackets and why a function is usually better.

    mutex

    A lock that exactly one thread can hold at a time, used to protect shared data.

    It converts a race condition into a queue. Forgetting to unlock one is how a program hangs forever with no error message.

    null-terminated

    A string convention: the text runs until a zero byte, which marks the end.

    It means length costs a scan rather than a lookup, and that a missing zero byte turns every string function into a read off the end of the array.

    object file

    The compiler's output for one source file — machine code, not yet a runnable program.

    It is the thing the linker consumes. .o on Linux.

    opaque

    A type whose internals are declared in a header but defined only in one .c file, so callers can hold a pointer to it without seeing inside.

    It is C's version of a private member: the compiler enforces it, because code that cannot see the fields cannot depend on them.

    pointer

    A variable that holds a memory address rather than a value.

    The whole of C's power and all of its danger come from this one idea. Read the pointers section twice before moving on.

    race condition

    A bug where the result depends on which of two threads happens to get there first.

    It is not reproducible on demand, which is why sanitizers exist: you cannot find these by running the program until it fails.

    sanitizer

    A compiler option that adds runtime checks — -fsanitize=address,undefined — so a bad memory access reports itself instead of silently corrupting something.

    It roughly doubles runtime and is worth it on every debug build. Every solution in this file was run under it.

    segmentation fault

    The operating system killing your program because it touched memory it does not own.

    It is the good outcome. The bad outcome is touching memory you do own but did not mean to, which produces no message at all.

    signal handler

    A function the operating system calls when an event such as Ctrl-C arrives.

    It interrupts your program between any two instructions, so almost nothing is safe to call inside one — setting a flag and returning is the usual whole of it.

    stack frame

    The block of memory holding one function call's local variables and return address.

    It is created on call and destroyed on return, which is exactly why returning a pointer to a local variable hands back an address that no longer belongs to you.

    standard library

    The set of functions every C compiler provides, reached with #include.

    Far smaller than Python's or R's — no containers, no text type, no networking. Knowing its limits is knowing what you must write yourself.

    toolchain

    The collection of programs that turn source into a running binary: compiler, assembler, linker, and the standard library they target.

    Cross-compiling means using a toolchain that produces code for a different machine than the one you are on.

    translation unit

    One .c file plus everything its #includes pasted in — the compiler's actual unit of work.

    The compiler sees exactly one at a time and nothing about the others, which explains almost every confusing multi-file error.

    undefined behaviour

    A program construct the standard deliberately places no requirements on at all.

    The compiler may assume it never happens and optimise on that basis, so the visible symptom can appear far away from the cause — or only after you change something unrelated.

    VLA

    A variable-length array — an array whose size is a runtime value rather than a constant.

    Legal since C99 but optional since C11, and it puts an unbounded amount on the stack. The kernel bans them outright.

    volatile

    A promise to the compiler that a variable may change outside the visible flow of the program, so it must not cache the value in a register.

    It is for memory-mapped hardware and signal flags. It is not a threading tool and does not make anything atomic — a very common and expensive misreading.

    C1.0a Print one line first

    Write a program that prints exactly Hello, C followed by a newline, then exits successfully.

    What you should see 
    ./prob
    Hello, C
    Hint

    Every C program needs #include <stdio.h> to use printf, and a function called main that the operating system runs first. The \n inside the quotes is a newline character, not two characters — the backslash tells the compiler "this is not a literal backslash-n, it means: move to the next line". return 0; is how the program tells the shell it succeeded.

    Approach — no code

    Copy the shape from 0x00's second card almost exactly: #include <stdio.h>, then int main(void) { ... }, then one printf call with the exact text and a \n at the end, then return 0;. The only decision is getting the text inside the quotes byte-for-byte right — Hello, C, not hello, c or Hello C.

    Solution
    #include <stdio.h>

int main(void) {
    printf("Hello, C\n");
    return 0;
}

    printf does not add a newline for you — leave off the \n and the next thing your terminal prints lands on the same line, glued to your output. int main(void) means "this function returns a whole number, and takes no arguments"; the number it returns is the program's exit status, which C1.1 uses on purpose.

    Why it works — invariant and cost

    Nothing repeats and nothing is conditional, so the only claim to make is about the exit status: main returns 0, and 0 is the value a shell reads as success. Constant time.

    C1.0b Add two numbers you typed into the code first

    Declare two integer variables holding 4 and 7, add them, and print the result as 4 + 7 = 11.

    What you should see 
    ./prob
    4 + 7 = 11
    Hint

    A variable is a named box that holds one value of one type — int a = 4; makes a box named a that holds the whole number 4. %d inside a printf format string is a placeholder that gets filled in, in order, by the arguments listed after the comma.

    Approach — no code

    Three variables, one line each: declare a, declare b, declare a third holding a + b. Then one printf with three %d placeholders in the format string, filled in order by three arguments after the comma. Get the argument order wrong and it still compiles — it just prints the wrong numbers in the right sentence.

    Solution
    #include <stdio.h>

int main(void) {
    int a = 4;
    int b = 7;
    int sum = a + b;
    printf("%d + %d = %d\n", a, b, sum);
    return 0;
}

    You could write printf("4 + 7 = %d\n", a + b); instead and skip the sum variable — both compile. Naming the intermediate result is not required by the compiler; it is for the next person reading the code, who is usually you in three weeks.

    Why it works — invariant and cost

    Two named values, one sum, one line printed. The invariant worth stating is that int arithmetic here cannot overflow — 4 and 7 are nowhere near INT_MAX — which is exactly the assumption C2.1 removes.

    C1.1 Exit status that means something warm

    Write a program that prints its own name from argv[0], then exits with status 3. Confirm from fish that $status really is 3.

    What you should see 
    ./prob
    ./prob

    then echo $status prints 3

    Hint

    main returns int, and whatever number it returns becomes the program's exit status — a signal to whatever ran it (your shell, a script, another program) about whether it worked. 0 conventionally means success; anything else means some flavour of failure. In fish, run the program then echo $status to see the number the shell captured.

    Approach — no code

    Two facts meet here. main returns an int, and that int is the exit status — there is no separate call to make. And argv[0] is an ordinary string, so printing it is one line. The confirmation step is the real content: a program that exits 3 looks identical to one that exits 0 until you ask the shell.

    Solution
    #include <stdio.h>

int main(int argc, char **argv) {
    (void)argc;                 /* unused: silences -Wextra */
    printf("%s\n", argv[0]);
    return 3;
}

    argv[0] is the path used to invoke the program, not necessarily the file's name — run it as ./a.out and via a symlink and you get different strings. The (void)argc; cast is the standard way to tell the compiler an unused parameter is deliberate.

    Why it works — invariant and cost

    The program's only observable output is its exit status. The claim is that the status is a value you chose rather than whatever the last function happened to leave behind, which is what falling off the end of main gives you in C89.

    C1.2 Add two arguments warm

    Take two integers from the command line and print their sum. If the user supplies the wrong number of arguments, print a usage line to stderr and exit non-zero.

    What you should see 
    ./prob 2 3
    5
    Hint

    argv is the array of text the program was started with, and argc is how many entries it has — argv[0] is always the program's own name, so two real arguments means argc == 3, not 2. atoi ("ASCII to integer") turns a text argument like "3" into the number 3; use it for now — C8.3 replaces it with something that detects bad input instead of silently returning 0.

    Approach — no code

    Guard first, work second. Check argc before touching argv — two expected numbers means argc must be exactly 3, because slot 0 is the program name. The usage line goes to stderr rather than stdout so that redirecting the output to a file still shows you the complaint, and the non-zero exit is what lets a script tell failure from success.

    Solution
    #include <stdio.h>
#include <stdlib.h>

int main(int argc, char **argv) {
    if (argc != 3) {
        fprintf(stderr, "usage: %s <int> <int>\n", argv[0]);
        return 1;
    }
    printf("%d\n", atoi(argv[1]) + atoi(argv[2]));
    return 0;
}

    Usage messages belong on stderr, not stdout: that keeps them out of a pipe when someone runs ./add 2 3 | some-filter.

    Why it works — invariant and cost

    argc is checked before argv[1] and argv[2] are touched. That ordering is the invariant: every index read is one the guard has already proved exists. Constant time.

    C1.3 Celsius table core

    Print a table of Celsius to Fahrenheit from -40 to 100 in steps of 20, aligned in two columns with one decimal place.

    What you should see 
    ./prob
     Celsius Fahrenheit
     -40      -40.0
     -20       -4.0
       0       32.0
      20       68.0
      40      104.0
      60      140.0
      80      176.0
     100      212.0
    Hint

    %6.1f gives a width of 6 with one decimal. The conversion is f = c * 9.0 / 5.0 + 32.0 — write 9.0, not 9.

    Approach — no code

    A loop with a step, and one arithmetic trap. The conversion divides by 5, so if both operands are integers the division happens in integers and the fraction is gone before you multiply. Make at least one side a floating-point literal. Alignment is field widths in the format string, not spaces you type.

    Solution
    #include <stdio.h>

int main(void) {
    printf("%8s %10s\n", "Celsius", "Fahrenheit");
    for (int c = -40; c <= 100; c += 20) {
        double f = c * 9.0 / 5.0 + 32.0;
        printf("%8d %10.1f\n", c, f);
    }
    return 0;
}

    Writing 9 / 5 with int literals is the classic version of this bug: integer division gives 1, and every row is wrong by the same silent amount. One .0 is the whole fix.

    Why it works — invariant and cost

    The loop counter increases by a fixed step from a fixed start to a fixed bound, so it terminates for every input and runs a number of times you can compute before it starts. Each row is independent of the last — nothing carries.

    C1.4 Arguments in reverse core

    Print the command-line arguments in reverse order, one per line, excluding the program name.

    What you should see 
    ./prob a b c
    c
b
a
    Hint

    Start at argc - 1 and count down while the index is greater than 0.

    Approach — no code

    Count down rather than up: start at argc - 1 and stop at 1, so slot 0 (the program name) is excluded without a special case inside the loop.

    Solution
    #include <stdio.h>

int main(int argc, char **argv) {
    for (int i = argc - 1; i > 0; i--)
        printf("%s\n", argv[i]);
    return 0;
}

    Stopping at i > 0 rather than i >= 0 is what excludes argv[0]. Off-by-one at a loop boundary is the single most common C bug and it starts here.

    Why it works — invariant and cost

    Walking argv from argc - 1 down to 1 visits every argument exactly once and never reaches argv[0] or argv[argc]. The bound is decreasing and the floor is fixed, so it stops. O(n) in the number of arguments.

    ./prob

         1 -> 1

4294967295 -> 32
    Hint

    x & (x - 1) clears the lowest set bit. Loop until x is zero and count the iterations.

    Approach — no code

    Two shapes work. The plain one shifts right 32 times adding the low bit each pass. The better one clears the lowest set bit each pass and counts iterations, so it runs once per set bit rather than once per bit — worth knowing because it is the loop you will see in other people's code.

    Solution
    #include <stdio.h>
#include <stdint.h>

static int popcount(uint32_t x) {
    int n = 0;
    while (x) { x &= x - 1; n++; }   /* clears the lowest set bit each pass */
    return n;
}

int main(void) {
    uint32_t t[] = { 0u, 1u, 0xFFu, 0xFFFFFFFFu };
    for (size_t i = 0; i < sizeof t / sizeof *t; i++)
        printf("%10u -> %d\n", t[i], popcount(t[i]));
    return 0;
}

    x & (x - 1) works because subtracting 1 flips the lowest set bit to 0 and every bit below it to 1; the AND then clears all of them at once. The loop runs once per set bit, not once per bit width.

    Why it works — invariant and cost

    Each iteration clears the lowest set bit, so the number of remaining set bits strictly decreases and the loop runs once per set bit rather than once per bit — O(popcount) rather than O(width).

    Assign realloc's result to a temporary first. If it fails it returns NULL without freeing the old block, so assigning straight to your pointer leaks it.

    Approach — no code

    Keep a length and a capacity as separate numbers. When they meet, double the capacity and reallocate — into a temporary pointer, which you check before assigning back. Assigning the result straight into the original loses the old block on failure, and the old block was your data.

    Solution
    #include <stdio.h>
#include <stdlib.h>

int main(void) {
    size_t cap = 4, len = 0;
    int *a = malloc(cap * sizeof *a);
    if (!a) { perror("malloc"); return 1; }

    int v;
    while (scanf("%d", &v) == 1) {
        if (len == cap) {
            size_t ncap = cap * 2;
            int *tmp = realloc(a, ncap * sizeof *a);   /* never assign to a directly */
            if (!tmp) { perror("realloc"); free(a); return 1; }
            a = tmp; cap = ncap;
        }
        a[len++] = v;
    }

    printf("%zu values (capacity %zu):", len, cap);
    for (size_t i = 0; i < len; i++) printf(" %d", a[i]);
    putchar('\n');

    free(a);
    return 0;
}

    a = realloc(a, ...) is the canonical leak: on failure realloc returns NULL, the old block is still allocated, and you have just overwritten the only pointer to it. Doubling rather than growing by one is what makes n appends cost O(n) rather than O(n²).

    Why it works — invariant and cost

    Capacity is doubled rather than incremented, so n appends cost O(n) in total rather than O(n²). The invariant across the resize is that count <= capacity at every point, and that a failed realloc leaves the original block still valid and still owned.

        for (int c = 0; c < cols; c++) m[r][c] = r * cols + c;

    for (int r = 0; r < rows; r++) {
        for (int c = 0; c < cols; c++) printf("%3d", m[r][c]);
        putchar('\n');
    }

    for (int r = 0; r < rows; r++) free(m[r]);
    free(m);
    return 0;
}

    The failure path is the part people skip, and it is the part that leaks. Freeing in the reverse order of allocation, and unwinding exactly the rows already taken, is the same discipline the kernel enforces with its goto err_* ladders.

    Why it works — invariant and cost

    Rows are allocated one at a time, and the failure path frees exactly the rows already allocated — the loop counter is what makes that count correct. Every allocated row is freed exactly once on both paths.

    #include <stdio.h>

#define MAX_LEN   32

    Every word read is either found in the table and its count incremented, or inserted with a count of 1. The invariant is that the sum of all counts equals the number of words read — a property you can print and check.

    Solution
    #include <stdio.h>

       case where a runtime truncation check is worth writing. */

    const char *b = argc > 2 ? argv[2] : "b";
    const char *c = argc > 3 ? argv[3] : "c";

    printf("buf=[%s]\n", buf);
    if (need < 0)
        printf("encoding error\n");
    else if ((size_t)need >= sizeof buf)
        printf("truncated: needed %d bytes, had %zu\n", need + 1, sizeof buf);
    else
        printf("fit exactly, %d bytes used\n", need);

    char t[6];

    Every copy is bounded by the destination's size and the result is terminated explicitly. The claim is not 'the string fits' but 'whatever fits is a valid string, and truncation is visible' — which is what makes the bounded functions worth the extra argument.

    Approach — no code

    Push at the front, because it needs no traversal: allocate, point the new node at the current head, then make it the head. The free loop has one trap — read the next pointer before freeing the node, because after the free that field is not yours to read.

    Solution
    #include <stdio.h>

typedef struct Node { int v; struct Node *next; } Node;

static Node *push(Node *head, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return head;               /* caller keeps the old list on failure */
    n->v = v; n->next = head;
    return n;
}

static size_t len(const Node *h) {
    size_t n = 0;
    for (; h; h = h->next) n++;
    return n;
}

static void print(const Node *h) {
    for (; h; h = h->next) printf("%d%s", h->v, h->next ? " -> " : "\n");
}

static void destroy(Node *h) {
    while (h) { Node *next = h->next; free(h); h = next; }
}

int main(void) {
    Node *l = NULL;
    for (int i = 1; i <= 5; i++) l = push(l, i);
    print(l);
    printf("length %zu\n", len(l));
    destroy(l);
    return 0;
}

    destroy saves h->next before freeing h. Reading it afterwards is a use-after-free that usually appears to work, because the freed memory has not been reused yet — which is exactly why it survives testing and fails in production.

    Why it works — invariant and cost

    The list is a chain ending in NULL at every point between operations — that single claim is what makes traversal terminate. Insert at the head is O(1); every search is O(n) because there is no shortcut.

    C7.2 Growable vector core

    Wrap the C4.3 growth logic in a proper type with vec_push, vec_get and vec_free, returning a success flag from push.

    What you should see 
    ./prob
    0 1 4 9 16 25 36 49 64 81 
(len 10 cap 16)
    Hint

    Keep data, len and cap together in a struct. Grow by doubling, starting from a small non-zero capacity.

    Approach — no code

    Wrap the growth logic from the earlier problem behind a small interface: a data pointer, a length and a capacity, with push reporting success. Make the all-zeroes value a valid empty container and there is no initialiser to forget and no uninitialised-use bug available.

    Solution
    #include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>

typedef struct { int *data; size_t len, cap; } Vec;

static bool vec_push(Vec *v, int x) {
    if (v->len == v->cap) {
        size_t ncap = v->cap ? v->cap * 2 : 4;
        int *tmp = realloc(v->data, ncap * sizeof *tmp);
        if (!tmp) return false;
        v->data = tmp; v->cap = ncap;
    }
    v->data[v->len++] = x;
    return true;
}

static int  vec_get(const Vec *v, size_t i) { return v->data[i]; }
static void vec_free(Vec *v) { free(v->data); v->data = NULL; v->len = v->cap = 0; }

int main(void) {
    Vec v = { 0 };                      /* zero-init is a valid empty vector */
    for (int i = 0; i < 10; i++)
        if (!vec_push(&v, i * i)) { fprintf(stderr, "out of memory\n"); vec_free(&v); return 1; }

    for (size_t i = 0; i < v.len; i++) printf("%d ", vec_get(&v, i));
    printf("\n(len %zu cap %zu)\n", v.len, v.cap);

    vec_free(&v);
    return 0;
}

    Vec v = { 0 } being a valid empty vector means there is no separate vec_init to forget to call. Designing the all-zeroes state to be the correct initial state removes an entire class of uninitialised-use bug.

    Why it works — invariant and cost

    count <= capacity holds after every operation, and capacity only ever grows by doubling, so n pushes cost O(n) amortised. Every pointer into the buffer is invalid after a growth, which is the price of contiguity.

    #include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdbool.h>

#define NBUCKETS 16

typedef struct Entry { char *key; int val; struct Entry *next; } Entry;
typedef struct { Entry *b[NBUCKETS]; } Map;

/* FNV-1a: short, no tuning constants to look up, good enough for a bucket index */
static size_t hash(const char *s) {
    size_t h = 1469598103934665603UL;
    for (; *s; s++) { h ^= (unsigned char)*s; h *= 1099511628211UL; }
    return h % NBUCKETS;
}

static bool map_put(Map *m, const char *k, int v) {
    size_t i = hash(k);
    for (Entry *e = m->b[i]; e; e = e->next)
        if (strcmp(e->key, k) == 0) { e->val = v; return true; }   /* overwrite */

    Entry *e = malloc(sizeof *e);
    if (!e) return false;
    size_t n = strlen(k) + 1;
    e->key = malloc(n);
    if (!e->key) { free(e); return false; }
    memcpy(e->key, k, n);
    e->val = v; e->next = m->b[i]; m->b[i] = e;
    return true;
}

static bool map_get(const Map *m, const char *k, int *out) {
    for (const Entry *e = m->b[hash(k)]; e; e = e->next)
        if (strcmp(e->key, k) == 0) { *out = e->val; return true; }
    return false;
}

static void map_free(Map *m) {
    for (size_t i = 0; i < NBUCKETS; i++) {
        Entry *e = m->b[i];
        while (e) { Entry *n = e->next; free(e->key); free(e); e = n; }
        m->b[i] = NULL;
    }
}

int main(void) {
    Map m = { 0 };
    map_put(&m, "one", 1); map_put(&m, "two", 2); map_put(&m, "three", 3);
    map_put(&m, "two", 22);                      /* overwrite, not duplicate */

    const char *keys[] = { "one", "two", "three", "four" };
    for (size_t i = 0; i < 4; i++) {
        int v;
        if (map_get(&m, keys[i], &v)) printf("%-6s = %d\n", keys[i], v);
        else                          printf("%-6s = (absent)\n", keys[i]);
    }
    map_free(&m);
    return 0;
}

    The map owns a copy of every key. Storing the caller's pointer instead would be faster and would break the moment a caller passes a stack buffer that later goes out of scope — a dangling key that reads fine until the stack is reused. Ownership rules are the hard part of C data structures, not the algorithm.

    Why it works — invariant and cost

    Every key lives in the bucket its hash names, so a lookup that does not find it in that bucket can conclude it is absent without looking elsewhere. Expected O(1); worst case O(n) when every key collides, which a bad hash produces reliably.

    Implement a fixed-capacity FIFO over an array with head and tail indices that wrap. Distinguish full from empty, and reject a push when full rather than overwriting.

    What you should see 
    ./prob
    push 1 -> ok
push 2 -> ok
push 3 -> ok
push 4 -> ok
push 5 -> FULL
push 6 -> FULL
pop 1
pop 2
pop 3
pop 4
pop on empty -> EMPTY
    Hint

    The classic trick is to keep a separate count, or to leave one slot unused. A count is easier to get right.

    Approach — no code

    Keep a head index and a count, not a head and a tail. With two indices, full and empty are the same comparison and you have to waste a slot to tell them apart. The write position is the head plus the count, wrapped by the capacity.

    Solution
    #include <stdio.h>
#include <stdbool.h>

#define CAP 4

typedef struct { int buf[CAP]; size_t head, count; } Ring;

static bool ring_push(Ring *r, int v) {
    if (r->count == CAP) return false;
    r->buf[(r->head + r->count) % CAP] = v;
    r->count++;
    return true;
}

static bool ring_pop(Ring *r, int *out) {
    if (r->count == 0) return false;
    *out = r->buf[r->head];
    r->head = (r->head + 1) % CAP;
    r->count--;
    return true;
}

int main(void) {
    Ring r = { 0 };
    for (int i = 1; i <= 6; i++)
        printf("push %d -> %s\n", i, ring_push(&r, i) ? "ok" : "FULL");

    int v;
    while (ring_pop(&r, &v)) printf("pop %d\n", v);
    printf("pop on empty -> %s\n", ring_pop(&r, &v) ? "ok" : "EMPTY");
    return 0;
}

    Storing a count rather than comparing head and tail is what makes full and empty distinguishable — with two indices alone, head == tail means both. Rejecting rather than overwriting is a policy choice, and the right one whenever dropped data would be silent.

    Why it works — invariant and cost

    Head and tail advance modulo the capacity and the count distinguishes full from empty — without it the two states are identical. The buffer never allocates after construction, which is the reason to use one.

    C7.5 Reverse a linked list hard

    Reverse a singly linked list in place, iteratively, in one pass and without allocating. Print before and after.

    What you should see 
    ./prob
    5 -> 4 -> 3 -> 2 -> 1
1 -> 2 -> 3 -> 4 -> 5
    Hint

    Three pointers: previous, current, next. Save next before you overwrite current->next.

    Approach — no code

    Three pointers and one pass: the node before, the node you are on, and the node after. Save the one after, point the current node backwards, then step both forward. When you fall off the end, the new head is the pointer that was trailing.

    Solution
    #include <stdio.h>
#include <stdlib.h>

typedef struct Node { int v; struct Node *next; } Node;

static Node *push(Node *h, int v) {
    Node *n = malloc(sizeof *n);
    if (!n) return h;
    n->v = v; n->next = h;
    return n;
}
static void print(const Node *h) {
    for (; h; h = h->next) printf("%d%s", h->v, h->next ? " -> " : "\n");
}
static void destroy(Node *h) { while (h) { Node *n = h->next; free(h); h = n; } }

static Node *reverse(Node *head) {
    Node *prev = NULL;
    while (head) {
        Node *next = head->next;    /* save it: the next line destroys it */
        head->next = prev;
        prev = head;
        head = next;
    }
    return prev;
}

int main(void) {
    Node *l = NULL;
    for (int i = 1; i <= 5; i++) l = push(l, i);
    print(l);
    l = reverse(l);
    print(l);
    destroy(l);
    return 0;
}

    Saving next first is the whole algorithm — overwrite head->next before reading it and the rest of the list is unreachable and leaked. Reassigning the result (l = reverse(l)) matters too: the old head is now the tail.

    Why it works — invariant and cost

    Three pointers, and after each step the prefix already reversed is correct and the suffix is untouched. The loop ends when the unvisited suffix is empty. O(n) time, O(1) extra space, and every node is visited exactly once.

    Solution
    #include <stdio.h>

    What is written and what is read back are the same bytes, so the round trip is the identity — on this machine. The invariant does not survive a change of endianness or padding, which is why the record is checked field by field rather than assumed.

    if (end == s)             return false;   /* no digits at all */

    Each flag owns one bit and no two flags share one, so setting, clearing and testing are independent. The invariant is that the set of flags is exactly the set of bits — which fails the moment two constants collide.

    C9.4 Pack and extract hard

    Pack a date — year (12 bits), month (4), day (5) — into a single uint32_t, then extract the three fields back and confirm they round-trip.

    What you should see 
    ./prob
    packed 0x0FD513 -> 2026-08-19 ok
    Hint

    Shift each field to its position and OR them together. To extract, shift back down and mask off the width of the field.

    Approach — no code

    Decide the layout first and write it down: which field occupies which bits, adding to no more than 32. Packing is a shift left into position then an OR. Extracting is a shift right then an AND with a mask of the field's width. Round-tripping every field is the test.

    Solution
    #include <stdio.h>
#include <stdint.h>

#define YEAR_SHIFT  9
#define MONTH_SHIFT 5
#define DAY_SHIFT   0
#define YEAR_MASK   0xFFFu     /* 12 bits */
#define MONTH_MASK  0xFu       /*  4 bits */
#define DAY_MASK    0x1Fu      /*  5 bits */

static uint32_t pack(unsigned y, unsigned m, unsigned d) {
    return ((y & YEAR_MASK) << YEAR_SHIFT)
         | ((m & MONTH_MASK) << MONTH_SHIFT)
         | ((d & DAY_MASK) << DAY_SHIFT);
}

int main(void) {
    unsigned y = 2026, m = 8, d = 19;
    uint32_t p = pack(y, m, d);

    unsigned uy = (p >> YEAR_SHIFT)  & YEAR_MASK;
    unsigned um = (p >> MONTH_SHIFT) & MONTH_MASK;
    unsigned ud = (p >> DAY_SHIFT)   & DAY_MASK;

    printf("packed 0x%06X -> %04u-%02u-%02u %s\n", p, uy, um, ud,
           (uy == y && um == m && ud == d) ? "ok" : "MISMATCH");
    return 0;
}

    Masking on the way in as well as out is what stops an out-of-range month from corrupting the year field beside it. Named shifts and masks rather than literals is the difference between this being maintainable and being a puzzle in six months.

    Why it works — invariant and cost

    Pack and extract are inverses for every value inside the field width, and for no value outside it. The claim is bounded, and the bound is the shift count — that is why the mask is written next to it.

#include <string.h>

static size_t count(const int *a, size_t n) { (void)a; return n; }

/* 5 · return storage that outlives the call — heap, or a caller-supplied buffer */
static char *make_greeting(const char *who) {

    return s;                       /* caller frees */

int main(void) {

    buf[0] = 'A';

    i = i + 1;                      /* 3 · one modification, sequenced */

    The program has no defined behaviour, so it has no invariant: the sequence point rules do not order the reads and writes involved. What is true is that two compilers print different answers, and that neither is wrong.

    C10.1 Threads that sum a slice core

    Split an array of 1000 ints across four pthreads, each summing its own slice into its own result slot, then join and total them. Compile with -pthread.

    Compile with gcc -pthread. Omitting it can link but misbehave at runtime.

    What you should see 
    ./prob
    sum = 500500 (expected 500500)
    Hint

    Give each thread a struct with its range and a place to write. No shared mutable state means no lock is needed.

    Approach — no code

    Give each thread a small struct holding the bounds of its slice and a slot of its own to write into. Because no two threads write the same location, no lock is needed anywhere — that is the design being demonstrated. Join all four before reading any result, then total the slots on the main thread.

    Solution
    #include <stdio.h>
#include <pthread.h>

#define N 1000
#define T 4

typedef struct { const int *a; size_t lo, hi; long sum; } Job;

static void *worker(void *arg) {
    Job *j = arg;
    j->sum = 0;
    for (size_t i = j->lo; i < j->hi; i++) j->sum += j->a[i];
    return NULL;
}

int main(void) {
    int a[N];
    for (int i = 0; i < N; i++) a[i] = i + 1;

    pthread_t th[T];
    Job jobs[T];
    for (int t = 0; t < T; t++) {
        jobs[t] = (Job){ a, (size_t)t * N / T, (size_t)(t + 1) * N / T, 0 };
        if (pthread_create(&th[t], NULL, worker, &jobs[t]) != 0) {
            fprintf(stderr, "pthread_create failed\n");
            return 1;
        }
    }

    long total = 0;
    for (int t = 0; t < T; t++) { pthread_join(th[t], NULL); total += jobs[t].sum; }

    printf("sum = %ld (expected %d)\n", total, N * (N + 1) / 2);
    return 0;
}

    Each thread writes only to its own Job, so there is no race and no mutex — the fastest correct concurrency is the kind that does not share. Note the main thread only reads jobs[t].sum after pthread_join, which is what makes that read safe.

    Why it works — invariant and cost

    Each thread owns a disjoint slice, so no two threads write the same memory and no lock is needed. The invariant is disjointness — it is what makes the unsynchronised version correct here and incorrect in C10.2.

    C10.2 The race, and the mutex core

    Have four threads each increment a shared counter 100000 times. Run it without a lock and show the total is wrong, then add a mutex and show it is right.

    The unsafe total is expected to differ between runs. If it matches on your machine, raise ITERS or run it under -fsanitize=thread.

    What you should see 
    ./prob
    expected 400000
unsafe   392453 (lost updates)
safe     400000

    The unsafe total is different every run and is the whole point: it is lower than 400000 by an unpredictable amount. If yours happens to come out at 400000, run it again. The safe total must be exactly 400000 every time.

    Hint

    counter++ is a read, an add and a write — three steps that can interleave. A pthread_mutex_t around it makes them one.

    Approach — no code

    Run the unlocked version several times and record the totals: they will differ from each other and all fall short. The increment looks like one step but is a read, an add and a write, and two threads can read the same value before either writes. The lock makes those three steps indivisible; take it before the increment and release it immediately after.

    Solution
    #include <stdio.h>
#include <pthread.h>

#define T     4
#define ITERS 100000

static long unsafe_counter = 0;
static long safe_counter   = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

static void *bump(void *arg) {
    (void)arg;
    for (int i = 0; i < ITERS; i++) {
        unsafe_counter++;                  /* read-modify-write: races */
        pthread_mutex_lock(&lock);
        safe_counter++;
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

int main(void) {
    pthread_t th[T];
    for (int t = 0; t < T; t++) pthread_create(&th[t], NULL, bump, NULL);
    for (int t = 0; t < T; t++) pthread_join(th[t], NULL);

    printf("expected %d\n", T * ITERS);
    printf("unsafe   %ld %s\n", unsafe_counter,
           unsafe_counter == (long)T * ITERS ? "(got lucky this run)" : "(lost updates)");
    printf("safe     %ld\n", safe_counter);
    return 0;
}

    The unsafe counter may occasionally come out right, especially on a lightly loaded machine — which is exactly what makes data races so dangerous. -fsanitize=thread reports the race whether or not it manifested on this run, and that is the only reliable way to find them.

    Why it works — invariant and cost

    The mutex makes read-modify-write atomic, so the total is the sum of every increment. Without it the invariant 'total equals the number of increments' fails silently and intermittently, which is the worst way for it to fail.

    C10.3 fork and a pipe hard

    Fork a child that writes a message into a pipe; the parent reads and prints it, then waits for the child. Close the unused end in each process.

    What you should see 
    ./prob
    hello from the child
child exited with 0
    Hint

    pipe(fd) gives fd[0] to read and fd[1] to write. The reader will not see EOF until every copy of the write end is closed.

    Approach — no code

    Create the pipe before forking, so both processes inherit both ends. Then each closes the end it does not use — and that is not tidiness. The reader only sees end-of-input when every copy of the write end is closed, so a parent that keeps its own write end open waits forever for a child that has already finished.

    Solution
    #include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void) {
    int fd[2];
    if (pipe(fd) == -1) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }

    if (pid == 0) {                       /* child: writer */
        close(fd[0]);
        const char *msg = "hello from the child\n";
        write(fd[1], msg, strlen(msg));
        close(fd[1]);
        _exit(0);
    }

    close(fd[1]);                         /* parent must close its write end */
    char buf[128];
    ssize_t n;
    while ((n = read(fd[0], buf, sizeof buf)) > 0)
        fwrite(buf, 1, (size_t)n, stdout);
    close(fd[0]);

    int status;
    waitpid(pid, &status, 0);
    printf("child exited with %d\n", WEXITSTATUS(status));
    return 0;
}

    Forgetting close(fd[1]) in the parent is the classic hang: the parent still holds a write end open, so read never returns 0 and the loop waits forever. The child uses _exit rather than exit to avoid flushing the parent's stdio buffers a second time.

    Why it works — invariant and cost

    The write end is closed in the reader and the read end in the writer, so the reader sees end-of-file when the writer exits. Leaving one open is why a pipe program hangs rather than crashing.

    C10.4 container_of hard

    Implement the kernel's container_of macro and use it to recover a containing struct from a pointer to one of its members.

    What you should see 
    ./prob
    id=7 weight=1.5 tag=abc
recovered the same object: yes
    Hint

    offsetof from stddef.h gives the member's byte offset. Subtract it from the member's address and cast to the container type.

    Approach — no code

    The macro is given a pointer to a member, the type of the thing containing it, and the member's name. The standard offset operator tells you how far into that type the member sits; subtract that distance from the pointer and reinterpret the result. Everything else in the macro is bracketing so it survives being used inside a larger expression.

    Solution
    #include <stdio.h>
#include <stddef.h>

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

typedef struct { int id; double weight; char tag[8]; } Item;

int main(void) {
    Item it = { 7, 1.5, "abc" };

    double *w = &it.weight;                       /* a pointer to just one field */
    Item   *back = container_of(w, Item, weight); /* recover the whole struct */

    printf("id=%d weight=%.1f tag=%s\n", back->id, back->weight, back->tag);
    printf("recovered the same object: %s\n", back == &it ? "yes" : "no");
    return 0;
}

    This is how the kernel gets from a struct list_head * back to the object that embedded it, and it is why kernel lists need no void *data field. The cast to char * is required so the subtraction is in bytes — pointer arithmetic on double * would scale by 8.

    Why it works — invariant and cost

    Given a pointer to a member, the offset of that member within the struct is a compile-time constant, so recovering the containing object is exact arithmetic rather than a guess. It is undefined for a pointer that was never inside such a struct.

    C10.5 Intrusive linked list hard

    Build a minimal list_head: a struct with next and prev that gets embedded inside other structs. Link three items, walk the list, and recover each containing object with container_of.

    What you should see 
    ./prob
    bolts     12
nuts      30
washers    7
    Hint

    The list node holds no data at all. Use a circular list with a sentinel head — that removes every empty and end-of-list special case.

    Approach — no code

    The inversion takes a minute to see: the list nodes are not the objects, they are a small pair of pointers embedded inside the objects. So the list links node to node, and every time you want the actual item you convert a node pointer back into its owner with the macro from the previous problem. One list implementation then serves every type, which is exactly why the kernel does it this way.

    Solution
    #include <stdio.h>
#include <stddef.h>

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

struct list_head { struct list_head *next, *prev; };

static void list_init(struct list_head *h) { h->next = h->prev = h; }

static void list_add_tail(struct list_head *n, struct list_head *head) {
    n->prev = head->prev;
    n->next = head;
    head->prev->next = n;
    head->prev = n;
}

#define list_for_each(pos, head) \
    for (pos = (head)->next; pos != (head); pos = pos->next)

typedef struct { const char *name; int qty; struct list_head link; } Item;

int main(void) {
    struct list_head items;
    list_init(&items);

    Item a = { "bolts", 12, {0} }, b = { "nuts", 30, {0} }, c = { "washers", 7, {0} };
    list_add_tail(&a.link, &items);
    list_add_tail(&b.link, &items);
    list_add_tail(&c.link, &items);

    struct list_head *p;
    list_for_each(p, &items) {
        Item *it = container_of(p, Item, link);
        printf("%-8s %3d\n", it->name, it->qty);
    }
    return 0;
}

    The sentinel head is the trick worth taking away: because the list is circular and always contains the head, list_add_tail needs no "is it empty" branch and the walk needs no null check. An item can also sit on several lists at once by embedding several list_head fields — impossible with a list that owns a void *.

    Why it works — invariant and cost

    The node is embedded in the object rather than pointing at it, so the list allocates nothing and an object can be in several lists at once. The invariant is that every node reached is inside an object of the type the container-of assumes.

int main(void) {
    int a[] = {2, 4, 6, 8, 10, 12}, n = 6, key = 10;

    while (lo <= hi) {

        steps++;
        if (a[mid] == key) { found = mid; break; }
        else if (a[mid] < key) lo = mid + 1;
        else hi = mid - 1;
    }

    return 0;
}
    Answer 
    index 4 in 2 steps

    Binary search halves the range each step, so six elements need at most three comparisons. It requires the array to be sorted — run it on unsorted data and it returns a confident wrong answer rather than an error.
